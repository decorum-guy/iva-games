# Iva Games platform

Сервер аккаунтов, друзей, приватных комнат и адресных приглашений. Один Node-процесс владеет одной SQLite-базой платформы. Игровое состояние хранит отдельный runtime через `GameRegistration`; существующие шахматные серверы этим приложением не изменяются.

## Реализованная граница

- Email + пароль Argon2id, подтверждение почты, восстановление пароля, серверные сессии, выход и отзыв всех сессий.
- Публичные идентификаторы пользователей, отдельные отображаемые имена, заявки в друзья, принятие/отклонение/отмена, удаление и направленные блокировки.
- Приватные комнаты, явные приглашения друзей, резерв на две минуты и отдельный вход, готовность, изменение вместимости, передача создателя, исключение и закрытие lobby.
- Отдельные места ботов для игр, которые действительно их поддерживают. Бот не имеет аккаунта, email или cookie. Сложность и профиль входят в зафиксированный состав партии.
- Долговечная процедура запуска: замороженный состав, устойчивый `startCommandId`, повтор при неизвестном результате, привязка `matchId`, получение персонального состояния и передача игровых действий.
- Реальный технический runtime `platform-lab` для проверки состава, скрытых действий, восстановления и ботов. Это проверочная партия, а не реализация «Района».
- Необязательная Telegram-привязка: одноразовый deep link, кандидат из приватного чата, код в боте и явное подтверждение на сайте в исходной сессии. Отдельный выбор согласия на уведомления, отключение, отвязка и долговечная очередь приглашений.

`remorse` и `overdrive` возвращаются в каталоге как `unavailable`: их существующая сеть ещё не адаптирована к аккаунтам. `district` и `harbor` имеют статус `planned`. Запустить их через платформу нельзя до подключения настоящего адаптера.

Telegram по умолчанию выключен. Без полной явной конфигурации `GET /telegram` возвращает `available: false`. При включении сервер использует `packages/telegram-transport` с обязательным маршрутом через прокси kz-bot; прямого обхода при ошибке нет. В этой работе сценарий проверяется подставным транспортом, реальные бот, webhook и доставка не активировались.

## Локальный запуск

Из корня репозитория:

```sh
npm ci
npm run dev:platform
```

Во втором терминале:

```sh
npm run dev:portal
```

Платформа по умолчанию слушает `127.0.0.1:4310`, портал — `127.0.0.1:5175`. Vite передаёт `/api/platform` на сервер с исходным Host. Использовать один и тот же hostname в браузере и `PORTAL_ORIGIN`.

По умолчанию development использует **файловый почтовый ящик** `.runtime/platform-mail`: письма `.eml` содержат ссылки подтверждения и восстановления. Никакая почта не отправляется. Ящик не раздаётся HTTP-сервером; он доступен только локальному разработчику. В Git он не попадает. Файлы создаются с правами `0600`, каталог — `0700`. Production и доступ по внешнему HTTP с таким режимом запрещены.

Ссылку из локального письма открывают обычным образом: GET показывает форму, только явное подтверждение POST потребляет токен. API регистрации и логи не содержат проверочных токенов. Подтверждённый email обязателен для друзей и новых комнат.

Для сборки и запуска уже собранного сервера:

```sh
npm run build:foundation
npm run start:platform
```

Чтобы сервер также раздавал готовый портал, установить `PORTAL_DIST_DIRECTORY=apps/portal/dist` и настроить `PORTAL_ORIGIN` на его фактический origin. В production это HTTPS origin reverse proxy; напрямую сервер остаётся за заданным сетевым периметром.

## Конфигурация

| Переменная | Назначение |
|---|---|
| `NODE_ENV=production` | Включает обязательный HTTPS и запрет файловой почты |
| `PORTAL_ORIGIN` | Единственный канонический адрес сайта без пути, query и учётных данных |
| `PLATFORM_HOST`, `PLATFORM_PORT` | Адрес bind; development по умолчанию только loopback, порт 4310 |
| `PLATFORM_ALLOWED_ORIGINS` | Точный список разрешённых Origin через запятую; по умолчанию origin портала |
| `PLATFORM_ALLOWED_HOSTS` | Точный список Host, допускающий реальный reverse proxy или dev proxy |
| `PLATFORM_DATABASE_PATH` | База платформы; по умолчанию `.runtime/platform.sqlite` |
| `PLATFORM_LAB_DATABASE_PATH` | Отдельная база проверочной партии |
| `PORTAL_DIST_DIRECTORY` | Необязательная папка собранного frontend |
| `MAIL_MODE` | `file` для изолированной разработки либо `smtp` |
| `MAIL_FILE_DIRECTORY` | Приватная локальная папка development-писем |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE` | Почтовый сервер; TLS или обязательный STARTTLS с проверкой сертификата |
| `SMTP_USER`, `SMTP_PASSWORD` | Серверные учётные данные, если SMTP требует вход |
| `SMTP_FROM` | Реальный разрешённый отправитель писем |
| `TELEGRAM_ENABLED` | Явное `true` включает интеграцию; `false` отключает её, даже если настройки сохранены |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` | Серверный токен и username бота без `@`; bot ID выводится из токена |
| `TELEGRAM_WEBHOOK_SECRET` | Случайный секрет webhook, 32–256 символов `A–Z`, `a–z`, `0–9`, `_`, `-` |
| `TELEGRAM_PROOF_KEY_BASE64` | 32 случайных байта в стандартном base64 для шифрования кода подтверждения в очереди |
| `TELEGRAM_PROXY_URL` | Обязательный HTTP/HTTPS CONNECT либо `socks5h` proxy через kz-bot |

Наличие SMTP-конфигурации проверяется при старте production. Получение письма человеком проверяется отдельно: успешный SMTP-ответ означает принятие сервером, а не попадание в папку «Входящие». Регистрация при ошибке отправки возвращает явную ошибку с возможностью войти и повторно запросить письмо. Восстановление сохраняет одинаковый нейтральный ответ для существующих и отсутствующих адресов.

Не копировать рабочие токены, SMTP-пароли или SSH-ключи в конфигурацию из примеров. Внешняя почта, Telegram и публичное размещение не активируются запуском тестов.

### Подключение Telegram

Включение требует HTTPS origin и всех пяти значений Telegram. Неполная конфигурация останавливает старт с объяснением без вывода секретов. Значения Telegram без явного `TELEGRAM_ENABLED` также не активируются молча. Перед работой с живым маршрутом выполнить проверку доступа из [INFRASTRUCTURE_ACCESS.md](../../docs/iva-games/INFRASTRUCTURE_ACCESS.md); наличие переменной proxy само по себе не подтверждает SSH-доступ или маршрут.

Внешняя точка для Telegram — `POST /integrations/telegram/webhook`. Reverse proxy должен передавать её этому процессу, сохранять разрешённый Host и не записывать заголовок `X-Telegram-Bot-Api-Secret-Token` в логи. Webhook на стороне Telegram настраивается отдельно с тем же секретом. Приложение само не вызывает регистрацию webhook.

Ссылка подключения действует десять минут и привязана к конкретной сессии сайта. `/start` записывает кандидата и ставит в очередь зашифрованный код; аккаунт ещё не связан. Только POST с кодом из приватного чата, недавней проверкой пароля и явным `consent: true` либо `false` завершает привязку. Другой браузер, группа, пересланное сообщение и повтор старой ссылки не переносят аккаунт автоматически. Одна Telegram-личность не переносится между игровыми аккаунтами без явной процедуры отвязки.

Приглашение и его запись для сайта создаются в одной транзакции с enqueue Telegram. Очередь создаётся только для уже связанного получателя с согласием; старые приглашения после включения не рассылаются. Перед каждой попыткой worker заново проверяет адресата, дружбу, блокировки, привязку, настройку уведомлений, открытость комнаты, срок и вместимость. Worker отправляет не более одного сообщения одновременно и использует десятисекундный deadline. `429` повторяется с задержкой; потерянный ответ хранится как неизвестный результат, поэтому повтор может дублировать сообщение. Отписка прекращает следующие попытки, но не отзывает уже отправленный сетевой запрос.

Принятие сообщения Telegram API не означает, что человек прочитал его. Кнопка ведёт на адресное приглашение сайта: она сама не принимает приглашение и не занимает место. Состояния доставки отделены от состояния комнаты.

## Надёжность и права

Cookie в HTTPS — `__Host-iva_session; Secure; HttpOnly; SameSite=Lax; Path=/`, без Domain. Для изолированного HTTP development используется другое имя `iva_dev_session`. Идентификаторы сессий и почтовые токены хранятся только в виде SHA-256-хеша; пароли — отдельным Argon2id-профилем с собственной солью.

Каждая мутация проверяет точный Origin, сессию и CSRF. После асинхронного чтения тела сессия проверяется повторно. Вход перечитывает актуальный credential и создаёт сессию в одной синхронной транзакции после проверки пароля: concurrent reset не выдаёт новую сессию по старому паролю. Reauthentication и отзыв всех сессий также проверяют, что исходная сессия ещё действует.

HTTP-предел на один адрес — 3000 запросов в минуту; чтение ограничено отдельно на сессию, чтобы шесть участников за одним NAT или reverse proxy не блокировали друг друга обычным polling. У входа, создания аккаунтов, поиска и социальных действий отдельные более строгие ограничения. `X-Forwarded-For` не считается доверенной идентичностью клиента.

Членство и вместимость защищены SQLite-транзакциями и уникальными индексами. Повтор операции с `Idempotency-Key` возвращает прежний результат; изменение payload под тем же ключом отклоняется. Срок хранения receipt — сутки. Разрыв HTTP-соединения не освобождает место; явный выход из lobby — отдельная операция.

Runtime-вызовы ограничены дедлайном 3 секунды. Запуск с неизвестным исходом остаётся `starting` и повторяется с тем же ID, а не создаёт другой матч. Независимые комнаты согласуются ограниченным параллелизмом. Дедлайн не отменяет работу стороннего runtime автоматически, поэтому его собственная долговечная идемпотентность обязательна. HTTP начинает слушать до первого полного прохода согласования сохранённых комнат.

## Хранилище и восстановление

SQLite использует WAL, `synchronous=FULL`, foreign keys, busy timeout и схему `user_version=1`. Переданный файл БД получает права `0600`. Не запускать несколько владельцев одного файла и не копировать только основной файл активной WAL-базы.

`PlatformService.backup(destination)` использует SQLite online backup API и создаёт согласованный снимок с правами `0600`. Тест восстановления открывает снимок отдельным экземпляром и сверяет аккаунт и социальную связь. Для полноценного восстановления партии нужны также согласованные резервные копии конкретных игровых runtime; один platform backup не содержит их состояние.

## Проверки и пределы

```sh
npm run check:platform
npm run build:foundation
```

Изолированный набор backend:

```sh
npx vitest run --config apps/platform/vitest.config.ts
npx tsc --noEmit -p apps/platform/tsconfig.json
```

Тесты используют независимые HTTP cookie-клиенты, SQLite-файлы во временных каталогах, подставную почту и подставной Telegram-транспорт. Они проверяют чужие адресные приглашения, гонку за последнее место, состояние принятия отдельно от входа, блокировку, готовность, ботов, перезапуск платформы и runtime, скрытые действия, повтор команд, потерянный ответ запуска, конкурентный reset, отозванную сессию при задержанном HTTP body, зависший runtime и восстановление backup. Для Telegram проверяются HTTP-стык, webhook-secret, привязка к исходной сессии, отсутствие автоматического consent, повторы update, очередь, отзыв разрешения, ошибки доставки и восстановление долговечных записей.

Это не проверка реальной SMTP-доставки, Telegram webhook, публичного TLS, интеграции шахмат или человеческой партии в «Район». Точный отчёт текущей интеграции хранится в общих документах Iva Games.

Контракт HTTP: [API_CONTRACT.md](API_CONTRACT.md).
