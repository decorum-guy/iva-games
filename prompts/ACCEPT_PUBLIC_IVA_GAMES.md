# Iva Games: публичная приёмка, автодеплой и диагностика из чата

Ты — локальный исполнитель на моём Mac. Продолжи существующий проект `decorum-guy/iva-games`: доведи публичную приёмку, проверь обновление работающего сайта и однократно установи ограниченный диагностический доступ через GitHub Actions. Исправляй обнаруженные дефекты, проверяй результат и публикуй законченные этапы. Не запускай первоначальную установку VPS заново.

## 1. Найди актуальное состояние

Найди существующий clone в `~/Developer`, проверь remote, незакоммиченные изменения и свежую `origin/main`. При занятой копии создай отдельный worktree. Проверенная вершина предыдущей передачи — `eeb886a5eaae1823716f0f9d3505350d37ecb346`; это историческая точка, а не требование откатиться к ней. Сохрани новые коммиты. PR №10 Colossus и №14 Gemini/AGY относятся к другим задачам.

Прочитай верхние актуальные разделы `AGENTS.md`, затем:

- `docs/iva-games/PROJECT_STATUS.md`;
- `docs/iva-games/BUILD_STATUS.md`;
- `docs/iva-games/TELEGRAM_ACCOUNTS.md`;
- `docs/iva-games/VPS_ACTIVATION_2026_11_26.md`;
- `docs/iva-games/RELEASE_IVA_GAMES_PRO.md` и раздел автопубликации в `ARCHITECTURE.md`;
- `docs/iva-games/CHAT_SERVER_ACCESS.md`;
- `.github/workflows/iva-release-check.yml` и отдельный workflow диагностики, названный в документе доступа.

Старые разделы про обязательный SMTP, запрет Telegram и первичное подключение root описывают предыдущий этап. Сейчас production использует Telegram-аккаунты и `MAIL_MODE=disabled`. Последний опубликованный статус был `WAITING_DNS`, а доставка образов — `STAGED`; узнай фактическое состояние, прежде чем выбирать действия.

## 2. Продолжи существующую активацию

Используй настроенный `ssh iva-games`: администратор `iva-admin`, порт `2233`, ключ и Apple Keychain уже подготовлены. Первоначальный пароль root, новый порт и SMTP не нужны. Сохрани доступ администратора, ограниченного `iva-deploy`, правила firewall, fail2ban, резервные копии, ACME и действующий таймер. Повторно проверяй инфраструктуру при признаках конкретной неисправности; не повторяй перезагрузку, ротацию ключей или переключение SSH ради отчёта.

Начни с чтения `/var/lib/iva-games/activation/state.json`, текущих SHA и digest из `/etc/iva-games/pins.json`, состояния таймера, сервисов и признаков незавершённого выпуска. Зафиксируй SHA исходников отдельно от SHA фактически запущенных образов. Не публикуй содержимое environment, ключи, токены, коды входа или персональные данные.

При `WAITING_DNS` проверь оба имени — `iva-games.pro` и `chess.iva-games.pro`, ответы двух резолверов, A/CNAME и AAAA. Записи меняет владелец; не обходи проверку согласованного DNS и не форсируй получение сертификатов. При `WAITING_TLS` или ошибке найди конкретную причину и исправь её минимально. При `WAITING_CONFIG` применяй актуальную конфигурацию Telegram-only: SMTP требуется только для явно выбранного `MAIL_MODE=smtp`. Не меняй `initial_sha` или pins только ради зелёного статуса: сначала сопоставь принятый SHA, CI, образы и фактический runtime.

`STAGED` означает подготовленный выпуск, `DEFERRED` — отложенное обновление до допуска, `ACTIVE` — пройденную активацию HTTPS, `DEPLOYED` — завершённое обновление после неё. `UNCHANGED` не доказывает новый выпуск. Если DNS пока блокирует активацию, выполни доступную локальную работу и настройку диагностики; явно оставь публичные проверки открытыми.

## 3. Установи диагностический канал один раз

Следуй `CHAT_SERVER_ACCESS.md`. Из проверенного checkout установи `deploy/iva-games/install-ops.sh` через существующего администратора; обычный автодеплой контейнеров не устанавливает корневые серверные помощники. Не запускай для этого первоначальный `install-host.sh`.

Нужны отдельный пользователь `iva-ops` и отдельный ключ GitHub Actions. Сохрани ограничения `iva-deploy`. Диагностический ключ должен запускать только фиксированную операцию чтения, без произвольной команды, PTY, forwarding, членства в Docker и общего sudo. Проверь разрешённый снимок состояния и отказ запрещённых операций. Вывод содержит только разрешённые поля; сырые environment, журналы, базы и полный `docker inspect` в Actions не попадают.

Настрой указанные в документе secrets/variables и выполни первый запуск отдельного диагностического workflow через локальный авторизованный `gh workflow run` или GitHub UI. В текущем чате есть повтор конкретного job, но нет инструмента `workflow_dispatch`: нужен настоящий первоначальный запуск. Запиши ссылку, run ID, job ID, SHA и время полученного снимка. Повтор диагностики не должен запускать deploy или зависимые операции изменения сервера.

У GitHub повтор доступен в пределах 30 дней исходного запуска, максимум 50 повторов; он использует первоначальные SHA/ref и права исходного исполнителя. Проверь механизм свежего диагностического запуска после следующих выпусков. Работающий локальный SSH или наличие YAML ещё не подтверждают доступ из чата: итоговая приёмка канала включает реальный повтор диагностического job из чата и чтение нового результата. Если эту часть должен выполнить агент в чате, передай точные идентификаторы и оставь её явно ожидающей.

## 4. Прими настоящий вход через Telegram

После `ACTIVE` открой публичный HTTPS в браузере. Пройди «Продолжить через Telegram» → личный чат выделенного бота → Start → полученный код → **тот же браузер, который начал вход**. Первый вход должен создать профиль с уникальным `@именем` и отображаемым именем; повторный вход возвращает тот же аккаунт. Проверь выход, обновление страницы и сохранение профиля. Записывай результат доставки без самого кода.

Бот уже подключали: сначала проверь его состояние, не повторяй настройку автоматически. Если требуется исправление, используй `telegram-auth-setup-mac.py` и существующий маршрут через `kz-bot` по документу. Токен BotFather вводится скрыто на Mac и не размещается в VPS environment. Runtime отвечает методом Bot API непосредственно в webhook-ответе; ему не нужен исходящий Telegram-прокси. Не путай этот вход с независимой старой интеграцией исходящих приглашений.

Используй только аккаунт владельца и заранее разрешённый второй тестовый аккаунт. Если нужен ручной Start, код или второй получатель, подготовь конкретный шаг и попроси только недостающее действие. Не рассылай сообщения другим людям.

## 5. Проверь профиль и друзей

На сайте проверь инициалы и выбор одной из шести фигур, отображаемое имя, поиск по `@имени` и отправку заявки. В настоящем боте проверь `/profile`, `/friends`, `/requests`, `/name`, выбор аватара и штатные стили кнопок. Изменения должны согласованно отражаться в профиле, друзьях, заявках и комнатах. Поиск и новые заявки остаются на портале.

Двумя разрешёнными аккаунтами прими и отклони заявки через оба интерфейса. Проверь исчезновение обработанной заявки и правильный состав друзей после обновления. Повторные, устаревшие и чужие callbacks проверь контролируемыми тестами на изолированных данных; повтор не создаёт второй эффект, чужое действие не меняет заявку. Не подделывай действия случайных пользователей в production. Mock-тест подтверждает обработчик, но реальную доставку и работу кнопки отмечай только после наблюдения в Telegram.

## 6. Проверь портал и гостевые шахматы

Снаружи открой `https://iva-games.pro/`, `/chess`, `/games`, `https://chess.iva-games.pro/` и `/overdrive/`. Каталог доступен без входа, разделы понятны, будущие игры не выдают себя за готовые. Проверь ключевые сценарии RU/EN, клавиатуру, модальные окна и узкий экран; физический телефон укажи отдельно от эмуляции.

Для каждой шахматной игры используй два независимых гостевых браузерных контекста: создание комнаты, подключение, ходы обеих сторон, согласованное состояние, краткая потеря сети, возвращение, результат и реванш. Не перезапускай общий сервер во время чужих партий. Общий аккаунтный адаптер шахмат остаётся отдельным этапом. Для портала проверь комнату, приглашение и короткую партию в доступную игру с сохранением результата.

Сохрани принятые правила энергии v2, баланс, модели, падение короля и все 20 звуков Форсажа, включая приглушённый общий ход. Не проводи новое творческое переозвучивание или перебалансировку. Не останавливай локальные демонстрации и не удаляй сохранения.

## 7. Подтверди автодеплой после ACTIVE

Публикуй законченные исправления отдельными коммитами и PR, проверяя текущую удалённую вершину перед каждым обновлением. Не используй force-push и не обходи обязательные проверки. Выполни контролируемый push в `main` после приёмки изменений и `ACTIVE`; дождись CI, публикации образов и фактического `DEPLOYED <полный SHA>`.

Сопоставь новый SHA, pins, HTTPS и диагностический снимок. До и после зафиксируй digest и идентификаторы контейнеров. Для изменения только platform шахматный digest и работающий chess-контейнер должны сохраниться. Используй реально нужное небольшое исправление, если оно найдено при приёмке. Если выпуск меняет только документацию и оба приложения сохранены, честно назови его проверкой выпуска без замены приложений; не выдавай её за проверенную замену platform.

При сбое исследуй pending/error и текущие данные; не восстанавливай старую базу поверх действующей. Не запускай повтор deploy вслепую. Дополнительные тесты выбирай по исправленному риску и обязательным CI, а не повторяй всю историческую приёмку.

## 8. Передай проверенный результат

Обнови верхний актуальный статус и отдельный отчёт: принятый SHA, ссылки на CI/выпуск, состояние сервера, digest до/после, реальные браузерные наблюдения, доставка кода и кнопки Telegram, результат диагностического канала. Отдели выполненное от открытого, приложи ссылки на законченные опубликованные этапы и оставь полезную демонстрационную вкладку. Не включай секреты. Завершай конкретным результатом и необходимым следующим действием, если внешний шаг остался заблокирован.
