# Задание локальному агенту: первый публичный выпуск Iva Games

Выполняй это задание, когда владелец передаст его для начала публикации. Цель — довести принятый кандидат до работающих публичных адресов и настроить дальнейшее обновление выбранных сервисов из GitHub. Читай действующие инструкции репозитория; выполняй уже разрешённые действия без повторных запросов на обычные проверки и исправления.

## 1. Получить точный кандидат

Найди существующий clone в `~/Developer`, проверь remote и незакоммиченные изменения. Используй отдельный worktree при занятых рабочих копиях. Не останавливай демонстрации 4173, 4185 и 5175/4310 и не перезаписывай их базы.

Проверь реальную голову PR №9 и изменения после проверенного SHA. Сохрани более новую работу. Документальная правка не требует повторять всю игровую приёмку; изменения runtime проверяй по их риску. Не сливай несколько старых PR вслепую поверх уже собранной истории. Публикуй законченные этапы отдельными коммитами без force-push.

## 2. Установить фактическую инфраструктуру

По уже доступному локальному контексту и репозиторию Control Panel найди описание серверов и SSH alias. Читай только относящиеся к задаче настройки; не выводи приватные ключи, токены и пароли.

Сначала read-only: какой сервер владелец назначил для игр, какие домены/сервисы и proxy уже работают, доступны ли Docker/Compose, порты и ресурсы. `kz-bot` назначен маршрутом Telegram, это само по себе не назначение сервера для игр. Последний отчёт уже подтверждает SSH с Mac; проверяй текущее состояние, не ремонтируй исторический timeout без воспроизведения. Выполни `npm run check:kz-bot` и отдельно проверь маршрут из будущего runtime при включении Telegram.

Если целевой сервер или почтовый провайдер нигде не выбраны, подготовь всё доступное: точные образы, конфигурацию, список необходимых DNS-записей с фактическим IP и предложение по размещению. Затем задай один конкретный вопрос о недостающем выборе. Не запрашивай пароли в чат и не заказывай платные сервисы самостоятельно. Если выбор и разрешение уже есть в контексте, продолжай без повторного согласования.

## 3. Подготовить безопасный первый запуск

Следуй `RELEASE_IVA_GAMES_PRO.md`, используя точный принятый SHA и неизменяемые теги образов. Образы с GitHub CI не опубликованы в registry — собрать или опубликовать собственные реальные образы выбранным способом.

Настрой приватные env-файлы вне checkout и отдельные постоянные volumes. Внимательно проверь исходные имена БД Форсажа: прежний default мог быть `remorse.sqlite.overdrive.sqlite`, новый шаблон явно задаёт `overdrive.sqlite`. Переноси согласованную копию с проверкой; не принимай появление пустой БД за успешную миграцию. Демонстрационные аккаунты и файловую почту не переносить в публичные данные.

Почта в production — реальный SMTP для подтверждения аккаунтов и восстановления. `.invalid`-значения из CI разрешены только в изолированном недоставляющем CI; это не рабочая конфигурация. Настройки домена отправителя взять у выбранного провайдера. Telegram требует выделенного бота Iva Games, явного прокси через `kz-bot`, постоянного proof key, HTTPS и webhook. Не переиспользовать бот другого проекта и не включать прямой fallback. Реальные тестовые письма и Telegram-приглашения отправлять только явно разрешённому владельцем получателю.

Проверь Compose на целевой версии, права volumes, health и восстановление backup в **новый** отдельный volume. Замена контейнера в CI не заменяет эту проверку процедуры backup/restore. Существующий reverse proxy не заменять целиком: добавить сайты в его конфигурацию. Отдельный Caddy из шаблона использовать там, где он не конфликтует с другими сайтами.

## 4. Опубликовать и пройти внешний сценарий

При наличии разрешённого доступа настрой A/AAAA только для реально работающих адресов, запусти сервисы и проверь публичный HTTPS. Старые домены `chess-2.online` и `remorse.chess-2.online` не выключать побочным действием.

Проверь снаружи каталог и гостевые ссылки, регистрацию/подтверждение на разрешённых адресах, дружбу, приглашение, комнату «Пробного стола» с ботами. В двух независимых браузерных контекстах сыграй отдельную гостевую партию в обе шахматные игры, проверь reconnect и перезапуск на изолированной тестовой комнате. Новая партия Форсажа должна быть v2; согласованная прежняя v1 должна сохранить свои правила.

Пройди новые ссылки визуально на RU/EN. Зафиксируй отдельно, был ли физический телефон и субъективное прослушивание: эмуляцию и измерение аудиофайла не считать этими проверками. Не усложняй UI техническими оговорками; обычные действия и ошибки должны оставаться короткими.

## 5. Настроить дальнейшее обновление из GitHub

После принятого первого запуска настрой автоматизацию под фактический сервер/registry. Обновлять только изменившийся сервис; изменения общего пакета должны учитывать всех его потребителей. Портал и шахматы — разные образы и volumes, а обе шахматные игры сейчас находятся в одном сервисе.

Используй ограниченный доступ развёртывания, реальные GitHub secrets/environment, последовательное выполнение выпусков и сохранённый предыдущий совместимый образ. Не добавляй ключи в репозиторий. Проверяй health после обновления и совместимость данных перед откатом. Откат образа не должен автоматически восстанавливать старую базу и терять новые действия игроков. Обновление выбранного сервиса может оборвать его соединения; не обещай бесшовный релиз и учитывай активные партии.

Проверь механизм на контролируемом выпуске и зафиксируй фактические SHA, какие контейнеры сменились и какие не перезапускались. Наличие YAML без успешного запуска не считать работающим автодеплоем.

## Результат

Оставь проверенные публичные ссылки, SHA и идентификаторы образов, способ обновления/отката и подтверждённый backup/restore. В отчёте раздели публично работающие функции, доставку почты, Telegram, автодеплой и оставшиеся конкретные шаги. Открой одну итоговую вкладку портала для владельца, сохраняя остальные рабочие приложения. Не называй весь выпуск завершённым, если вместо реальных адресов работает только localhost или отсутствует обязательная почта аккаунтов.
