## 2. Установить фактическую инфраструктуру

По уже доступному локальному контексту и репозиторию Control Panel найди описание серверов и SSH alias. Читай только относящиеся к задаче настройки; не выводи приватные ключи, токены и пароли.

Сначала read-only: какой сервер владелец назначил для игр, какие домены/сервисы и proxy уже работают, доступны ли Docker/Compose, порты и ресурсы. `kz-bot` назначен маршрутом Telegram, это само по себе не назначение сервера для игр. Последний отчёт уже подтверждает SSH с Mac; проверяй текущее состояние, не ремонтируй исторический timeout без воспроизведения. Выполни `npm run check:kz-bot` и отдельно проверь маршрут из будущего runtime при включении Telegram. При выключенном Telegram недоступность этого маршрута зафиксируй как оставшуюся работу интеграции; она не блокирует публикацию сайта.

Если целевой сервер или почтовый провайдер нигде не выбраны, подготовь всё доступное: точные образы, конфигурацию и список необходимых DNS-записей. Фактический IP подставь после определения сервера. Затем задай один конкретный вопрос о недостающем выборе. Не запрашивай пароли в чат и не заказывай платные сервисы самостоятельно. Если выбор и разрешение уже есть в контексте, продолжай без повторного согласования.

## 3. Подготовить безопасный первый запуск

Следуй `RELEASE_IVA_GAMES_PRO.md`, используя точный принятый SHA и неизменяемые теги образов. Образы с GitHub CI не опубликованы в registry — собрать или опубликовать собственные реальные образы выбранным способом.

Настрой приватные env-файлы вне checkout и отдельные постоянные volumes. Внимательно проверь исходные имена БД Форсажа: прежний default мог быть `remorse.sqlite.overdrive.sqlite`, новый шаблон явно задаёт `overdrive.sqlite`. Переноси согласованную копию с проверкой; не принимай появление пустой БД за успешную миграцию. Демонстрационные аккаунты и файловую почту не переносить в публичные данные.

Почта в production — реальный SMTP для подтверждения аккаунтов и восстановления. `.invalid`-значения из CI разрешены только в изолированном недоставляющем CI; это не рабочая конфигурация. Настройки домена отправителя взять у выбранного провайдера. Telegram оставить выключенным на первом запуске, пока его отдельная активация не подготовлена: он не блокирует сайт и сайт-приглашения. Для включения нужны выделенный бот Iva Games, явный прокси через `kz-bot`, постоянный proof key, HTTPS и webhook. Не переиспользовать бот другого проекта и не включать прямой fallback. Реальные тестовые письма и Telegram-приглашения отправлять только явно разрешённому владельцем получателю.

До первого запуска проверь `IVA_NETWORK_SUBNET`, `IVA_NETWORK_DYNAMIC_RANGE` и `CADDY_PROXY_IP` на конфликты с Docker/VPN/LAN маршрутами. Статический IP Caddy должен находиться внутри подсети и вне динамического пула; Compose передаёт тот же адрес обоим приложениям в `TRUSTED_PROXY_IPS`. Caddy перезаписывает `X-Iva-Client-IP` адресом TCP-клиента. Upstream-порты не публикуются. Для существующего proxy используй его точный доверенный адрес и тот же проверенный контракт; произвольным клиентским заголовкам доверять нельзя.

Проверь Compose на целевой версии, права volumes, health и восстановление backup в **новый** отдельный volume. Замена контейнера в CI не заменяет эту проверку процедуры backup/restore. Существующий reverse proxy не заменять целиком: добавить сайты в его конфигурацию. Для уже работающего Compose Caddy проверять конфигурацию через `deploy/iva-games/compose.sh exec -T caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`; второй `compose run caddy` конфликтует с его статическим IP. Отдельный Caddy из шаблона использовать там, где он не конфликтует с другими сайтами.

## 4. Опубликовать и пройти внешний сценарий

При наличии разрешённого доступа настрой A/AAAA только для реально работающих адресов, запусти сервисы и проверь публичный HTTPS. Старые домены `chess-2.online` и `remorse.chess-2.online` не выключать побочным действием.

Без аккаунта проверь снаружи `/`, `/chess` и `/games`: прямое открытие, обновление, переходы назад/вперёд, разделение карточек и гостевые ссылки. Затем пройди регистрацию/подтверждение и восстановление пароля на разрешённых адресах, дружбу, приглашение, комнату «Пробного стола» с ботами. В двух независимых браузерных контекстах сыграй отдельную гостевую партию в обе шахматные игры, проверь reconnect и перезапуск на изолированной тестовой комнате. Новая партия Форсажа должна быть v2; согласованная прежняя v1 должна сохранить свои правила.

Пройди новые ссылки визуально на RU/EN и проверь публичную версию на физическом телефоне, назвав фактически использованное устройство. Принятый звук Форсажа сохранить; проверка работы ресурса на новом origin не требует повторного художественного выбора. Браузерные результаты записывай по выполненным сценариям, не по наличию тестовых файлов. Не усложняй UI техническими оговорками; обычные действия и ошибки должны оставаться короткими.

## 5. Настроить дальнейшее обновление из GitHub

Автоматическое обновление сервера после push **ещё не реализовано и не настроено**: текущие workflows проверяют код и образы. После принятого первого запуска выполни отдельный контролируемый этап настройки под фактический сервер/registry. Обновлять только изменившийся сервис; изменения общего пакета должны учитывать всех его потребителей. Портал и шахматы — разные образы и volumes, а обе шахматные игры сейчас находятся в одном сервисе.

Используй ограниченный доступ развёртывания, реальные GitHub secrets/environment, последовательное выполнение выпусков и сохранённый предыдущий совместимый образ. Не добавляй ключи в репозиторий. Проверяй health после обновления и совместимость данных перед откатом. Откат образа не должен автоматически восстанавливать старую базу и терять новые действия игроков. Обновление выбранного сервиса может оборвать его соединения; не обещай бесшовный релиз и учитывай активные партии.

Проверь механизм на контролируемом выпуске и зафиксируй фактические SHA, какие контейнеры сменились и какие не перезапускались. Наличие YAML без успешного запуска не считать работающим автодеплоем.

## Результат

Оставь проверенные публичные ссылки, SHA и идентификаторы образов, способ обновления/отката и подтверждённый backup/restore. В отчёте раздели публично работающие функции, доставку почты, Telegram, автодеплой и оставшиеся конкретные шаги. Открой одну итоговую вкладку портала для владельца, сохраняя остальные рабочие приложения. Не называй весь выпуск завершённым, если вместо реальных адресов работает только localhost или отсутствует обязательная почта аккаунтов.
