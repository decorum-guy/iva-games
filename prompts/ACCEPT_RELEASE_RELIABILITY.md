# Локальному агенту: установить исправление автодеплоя и доказать изоляцию шахмат

Проект `decorum-guy/iva-games`, публичные адреса `https://iva-games.pro/`, `https://chess.iva-games.pro/`, `https://chess.iva-games.pro/overdrive/`. Продолжи разрешённое владельцем исправление выпуска после PR №20. Работа: принять код, точечно обновить обработчики на существующем VPS, выполнить первый инфраструктурный выпуск и затем проверить отдельное обновление только портала/Района. Новый игровой цикл Района разрабатывается отдельно; в этот выпуск его не включать.

Прочитай `AGENTS.md`, актуальный `docs/iva-games/BUILD_STATUS.md`, `RELEASE_RELIABILITY_2026_11_27.md`, `RELEASE_IVA_GAMES_PRO.md`, отчёт `VPS_ACTIVATION_2026_11_26.md` и фактический diff ветки `fix/release-isolation-20261127`. Текущая передача и исследование Района опубликованы отдельно в PR №21; если он ещё не в main, прочитай их из его ветки. Не применяй исторические требования про обязательный SMTP или отключённый Telegram.

## 1. Получить точный кандидат и прочитать состояние

- Найди существующий checkout, проверь незакоммиченные изменения, удалённые refs и PR. При необходимости сделай отдельный worktree. Не заменять чужую рабочую ветку.
- Сверь коммит проверяемого PR с CI. Ознакомься с реальным diff, исправь выявленный дефект в его рамках и опубликуй отдельным коммитом без force-push.
- Используй существующий Mac SSH alias `iva-games` и проектные ключи/Keychain из отчёта, проверяя доступ в текущем окружении. Не печатай пароли, токены, полные env или ключи. Ограниченный аккаунт CI `iva-deploy` не использовать как произвольный администраторский shell.
- На VPS прочитай `state.json`, `pins.json`, наличие `pending.json`/`deploy-error.json`, текущие ID/digest/StartedAt/RestartCount и Running/Paused для platform/chess/Caddy. Проверь здоровье трёх HTTPS endpoints. Проверенные файлы состояния сохранить приватно, в публичном отчёте — только нужные безопасные поля.
- Если остался pending или сервис paused/unhealthy, сначала установи реальное состояние и восстанови штатную работу. Не удаляй pending и не объявляй `DEPLOYED` вручную ради зелёного статуса.

## 2. Принять новый код до установки

Обязательные проверки кандидата:

```bash
npm ci --no-audit --no-fund
npm run check
python3 -B -m unittest discover -s deploy/iva-games -p 'test_*.py'
npm run build:all
npm run platform:smoke
```

Используй успешные актуальные CI выбранного SHA, не повторяй весь набор без причины на каждой машине. На Docker нужно дождаться реальных image gates обоих сервисов, включая остановку с незавершённым HTTP-body. Local shell/заглушка Docker не заменяют этот gate.

В изолированном Compose-проекте с отдельными томами проверь freeze/copy/WAL/unpause, оба SQLite-файла, восстановление в новые тома и ошибки копирования/проверки. Проверь внешний SIGTERM процесса activation: backup получает очистку, исходный контейнер возвращается к работе, lock удерживается до её завершения, неполная копия не признаётся годной. Отрицательные проверки не проводить на действующих игровых томах.

## 3. Один раз обновить host-скрипты до merge/доставки новых образов

Образы не заменяют `/opt/iva-games/deploy`. В текущем исправлении обязательны новые `activation.py`, `backup.sh` и `ci-deploy`. `github-main.py` и вычислитель fingerprint нужны runner/build, их не надо делать новыми root SSH entrypoints.

1. Подготовь точные файлы из проверенного коммита во временном каталоге, проверь SHA-256, `bash -n` и синтаксис Python без выполнения deploy.
2. Проверь, что другой выпуск не идёт. Возьми **тот же** `/var/lib/iva-games/activation/release.lock` через `flock` в эксклюзивном режиме, сохраняя его до конца установки. Lock-файл не удалять и не заменять новым inode.
3. Сохрани существующие три скрипта, их права/владельца/хеши в отдельный root-only каталог для отката именно установщика. Установи только проверенные замены с `root:root`, правами `0755`, безопасными временными файлами и заменой под lock. Проверь хеши и синтаксис установленных файлов.
4. Сверь фактические имена контейнеров и неизменность конфигурации. Не запускать повторно `install-host.sh`: это установщик пустого хоста, не updater. Не перезаписывать `release.env`, `platform.env`, `activation.json`, SSH, sudoers, webhook, proxy, Caddy, volumes или секреты шаблонами.
5. Отпусти lock и запиши, какой SHA/хеш каждого host-файла установлен. При ошибке установки верни прежние файлы под тем же lock, не меняя приложения и данные.

Не запускай автоматически публичный deploy из ветки: штатный обработчик принимает актуальный main после успешного CI. После подготовки хоста объедини принятый исправляющий PR обычным способом и дай штатному workflow выполнить доставку. Если main продвинулся, сначала интегрируй/проверь новый состав, не обходи проверку вершины.

## 4. Первый инфраструктурный выпуск

Он меняет оба server runtime и формат fingerprint. Поэтому **обновление обоих прикладных образов допустимо и ожидаемо**; Caddy сохраняется. Это не эксперимент «изменили только Район».

Уже запущенные старые процессы всё ещё имеют прежний shutdown: замена первого такого контейнера может упереться в старое 60-секундное поведение. Выбери контролируемый момент, сохрани данные, наблюдай фактический stop/exit и восстановление. Не обещай отсутствие паузы при этом ремонте. Не выдавай exit 137 или принудительную остановку за чистое завершение. После установки новых образов отдельно проверь их корректное завершение и перезапуск в изолированном окружении.

Проверить: исходные базы сохранены, копии без `INCOMPLETE` проходят проверку, контейнеры не paused, HTTPS здоров, `pending.json` отсутствует после успеха, state=`ACTIVE`, workflow действительно сообщает `DEPLOYED`, установленные pins соответствуют принятым digest. Открыть обе шахматные игры и Район, проверить сохранённую/возобновлённую партию.

Compatibility fingerprint консервативен: изменение общих исходников может запретить автоматический rollback даже без миграции таблиц. Не подменять метку совместимости и не откатывать автоматически данные. При неуспехе диагностировать текущую схему/версии и выбрать совместимое исправление вперёд либо отдельно обоснованный откат приложения.

## 5. Затем доказать независимость обычного обновления Района

Это отдельный контролируемый выпуск на базе уже установленного исправления.

- Сделай небольшую полезную правку именно портала/Района, не меняющую правила партии, например уточни существующую короткую подсказку по реальному наблюдению. Не создавай пустую техническую надпись в пользовательском UI. Покажи diff: в нём нет chess/server/shared/root-toolchain/Dockerfile.
- Перед merge вычисли отпечатки обеих версий и докажи: platform изменился, chess остался прежним. Документационный или пустой коммит, который не меняет образ platform, не проверяет замену контейнера.
- Открой независимые гостевые клиенты шахмат, создай собственную контрольную партию и начни обмен ходами. Не подключайся к чужим партиям. По возможности одновременно держи REMORSE и Форсаж.
- Зафиксируй container ID, image ID, StartedAt, RestartCount chess/Caddy. Снимай безопасный журнал Docker-событий выбранных контейнеров и внешних HTTPS-проб во время выпуска; без env/токенов.
- Объедини маленькую принятую правку и проследи настоящий workflow до результата. Ожидается `changed: ["platform"]` в `last-deploy.json`; ни backup, ни pause/unpause, ни stop, ни up/recreate chess/Caddy не происходят. Совпадения digest недостаточно: ID/StartedAt/RestartCount тоже те же.
- Контрольная шахматная партия продолжает принимать ходы без принудительного reconnect, состояния обоих клиентов согласованы. Одна проверка health после обновления не доказывает непрерывность.
- После выпуска проверь создание комнаты Района, выбор каждой карты, бота, старт, действие и возврат после обновления страницы по HTTPS. Используй существующий авторизованный аккаунт владельца; реальных друзей/сообщения без поручения не тревожь.

Если изоляция не выполнена, исправь конкретную причину, опубликуй и повтори только нужную приёмку. Не объявляй задачу законченной по зелёному CI.

## 6. Полный отчёт

Создай текстовый отчёт в `docs/iva-games` и обнови актуальный статус. Укажи:

- исходные и итоговые SHA, PR и реальные Actions runs;
- установленные host-файлы и хеши, порядок установки, неизменность конфигурации;
- какие причины установлены журналами, какие лишь воспроизведены на модели;
- результаты Docker/SQLite/сигналов и реальные коды завершения;
- первый инфраструктурный выпуск отдельно от второго portal-only;
- таблицу до/после для chess/Caddy и фактические события/HTTPS во время второго выпуска;
- состояние партии, комнаты Района, state/pins/pending после завершения;
- любые наблюдавшиеся перерывы и нерешённые ограничения.

Полные приватные логи, базы, трассы, видео и секреты остаются в игнорируемом локальном каталоге. В Git — воспроизводимые команды, тесты, безопасные измерения и краткий отчёт. Публикуй законченные этапы без force-push. Оставь рабочую вкладку для владельца и точные команды просмотра состояния.
