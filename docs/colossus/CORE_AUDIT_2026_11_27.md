# Колосс — ядро, помощник и Смотритель

27 ноября 2026 года, Москва. Продолжение реализации PR №10 в отдельной проверочной ветке. Источники требований: поручение владельца, `docs/chess-2/COLOSSUS_RULES.md`, `CARDS_AND_PRESENTATION.md` и фактический код. Параметры трёх обычных боссов, карт и сложности сохранены; учебные позиции — новая авторская реализация текущего запроса.

## Изменения

- **Смотритель / The Warden (`sentinel`)** — самостоятельный учебный противник с фиксированным циклом и телом 2×2. Создаётся только через `createTutorialGame`, имеет явный режим `tutorial`, не даёт рекорды обычной игры и не входит в охоту или поход.
- `createGame` отклоняет `sentinel` и режим `tutorial`, в том числе при передаче нетипизированного JSON. Проверка сохранения отклоняет перенос Смотрителя в обычную игру, обычного босса в обучение и совместное обучение. Редактор практики не принимает учебные состояния.
- Семь коротких упражнений: уход от объявленного луча; броня и HP; удар с отходом; луч и огонь; расходуемый щит; стоимость и срок карты; превращение пешки и победа на восстановлении. Последний удар действительно завершает бой победой через основное ядро.
- `lessonGuidance` возвращает текст следующего действия, клетки внимания и **подмножество настоящих `legalActions`**. Ограничения упражнения не подменяют правила. Перестановки учебной позиции объясняются в тексте.
- У помощника исправлен сбой при угрозе королю: полная оценка позиции повторно складывалась с полной оценкой действия и выходила за допустимый диапазон общего SDK. Теперь `fallbackScore` использует уже вычисленную оценку действия один раз. Даже при нулевом бюджете сохраняется допустимый спасительный ход.
- Поиск учитывает видимый предел раундов: завершение последней фазы без победы оценивается как поражение. Будущий добор или следующее неизвестное намерение помощник не читает. Версия адаптера поиска — `2`; правила обычной игры остаются `colossus-v1`.

## Добавление следующего босса

Общая геометрия тела, контакт, HP, броня, щиты, команды, сохранение и поиск не зависят от перечисления имён боссов.

| Место | Что добавить |
|---|---|
| `src/core/types.ts` | Добавить новый стабильный `BossId` в закрытое объединение; `HuntBossId` автоматически исключает только учебного Смотрителя. Идентификаторы существующих боссов не переименовывать. |
| `src/core/data.ts` | Определение в `BOSSES`: RU/EN, размеры, стартовая клетка, HP/броня. `HUNT_BOSSES` выводится из этих данных; `tutorialOnly` исключает учебные записи. |
| `src/core/bosses.ts` | Одну регистрацию `BOSS_BEHAVIORS`: генератор трёх паттернов, имя восстановления, приближение и обработчик особых карт. Общий `planIntent` сам выбирает план и замораживает объявленные клетки. |
| `src/core/data.ts`, соответствующий обработчик карт | Ровно три карточных определения со стабильными уникальными ID, RU/EN именами и описаниями. `BossCardId` уже является строкой; отдельное объединение имён расширять не требуется. Собственные варианты намерения подключаются через `cardPlans`; отсутствие обработчика оставит карты без эффекта. Обычный бой с включёнными картами требует ровно три карты при проверке сохранения. |
| `scripts/generate-colossus-cards.mjs` | Добавить каждый новый ID карты в `arts` и запустить генератор. `Card.tsx` читает `/assets/colossus/cards/<id>.svg` по `card.id`, не по `icon`. Имена берутся из карточного определения. Пропущенный SVG даст пустую иллюстрацию без ошибки TypeScript. |
| `scripts/generate-colossus-models.mjs`, `src/ui/PieceIcon.tsx` | Добавить GLB-builder в `bosses` и SVG-гравюру в типизированный `bossGlyphs`; запустить генератор моделей. `Board3D` загружает `/assets/colossus/models/<id>.glb`, оба рендера получают размеры из `BOSSES`. Отсутствующая GLB приводит к переходу в 2D, поэтому проверять нужно фактический 3D-рендер. |
| `apps/server/src/colossus/validation.ts` | Дополнительного списка ID нет: сетевое создание использует тот же `HUNT_BOSSES`. Новый обычный босс попадает в меню и сетевую проверку после регистрации; Смотритель остаётся исключённым. |
| `CAMPAIGN_BOSSES` | Непустая явно заданная последовательность; охота не добавляет босса в неё автоматически. Начало, привалы, завершение, границы индекса и счётчик UI берутся из этого списка. Состав менять только при отдельно принятом изменении похода с проверкой совместимости его сохранений; текущие три боя и их порядок сохранены. |

Текущий контракт v1: три паттерна и восстановление после трёх боевых ответов; шаги `move`/`rays`/`area`/`fire`; до восьми шагов в намерении; урон шага 0–3; итоговые максимумы HP и брони после множителя сложности не больше 100. Новая механика вне этого контракта требует явного расширения правил и проверки формата состояния.

Геометрия: основание на Y=0, центр по X/Z, одна клетка равна одной единице, меш внутри объявленного тела. Имена материалов `boss_armour`, `boss_heart`, `armour_fracture` подключают общие реакции. Камера сейчас рассчитывает верхнюю границу мира Y=2.2, модель ставится на Y=0.11, подпись попадания находится на Y=2.75. Более высокая модель требует изменения камеры/подписи; она не будет автоматически подогнана по размеру файла. Полный рецепт: [ASSETS.md](ASSETS.md).

Новые записи победы сохраняют `campaignBosses` — состав действительно пройденного похода. Старые записи без этого поля относятся только к исходным Регенту, Шпилю и Архивариусу. Новый босс не получает медаль от старой победы; сокращение истории сохраняет и медали отдельных боссов, и факт завершения похода.

Для нового босса нужны проверки всех паттернов, замороженной цели, контакта и границ тела, восстановления, карточных вариантов, сохранения/повтора и полная автоматическая партия. Существующий 3D E2E проходит по `HUNT_BOSSES` и проверяет загрузку/рендер каждой GLB; иллюстрации новых карт проверяются отдельно. Отдельная запись в каталоге боссов не доказывает качество игры с ним.

Дополнительная регрессия расширения использует изолированный модульный fixture: четыре боя с изменённым первым боссом, три привала с чередованием A/B/A, сохранение последнего индекса и отказ на неверных индексах. Отдельный обычный ID проверяет медали охоты, старого и явно записанного нового состава похода. Production-список при этом не изменяется.

После этой дополнительной правки выполнены `npm run colossus:test` — **136/136 тестов, 7 файлов**, TypeScript, целевой ESLint и `git diff --check` — успешно. Браузерная проверка нового изменения списка E2E относится к следующему запуску CI; результаты предыдущей ревизии не подменяют её.
