# Сетевая игра: первый рабочий этап

Решение по запросу владельца от 24 ноября 2026 года. **Статус на 25 ноября: реализация есть в исходниках, серверная приёмка пройдена; живая браузерная приёмка, активация на Mac и публичное размещение ещё не завершены.** Это исходный инженерный объём; фактическое состояние описано в `VALIDATION_RULES_AND_ONLINE.md`.

## Что должен получить игрок

В меню появляется «Играть по сети» / “Play online”. Игрок создаёт закрытую комнату, выбирает ник и сторону, копирует приглашение. Другой человек открывает ссылку на своём устройстве, вводит ник и занимает оставшееся место. После готовности обоих начинается обычная REMORSE: 3D/2D, все реакции, броски, счётчики, превращения, взятые фигуры, шах и мат. Поддерживаются RU/EN, ноутбук и телефон.

Первый этап — дружеские нерейтинговые партии без часов, публичного поиска соперника и чата. Это позволяет закончить саму совместную игру и восстановление соединения. Локальный Elo против ботов не становится сетевым рейтингом. Будущий общий рейтинг потребует серверных профилей и отдельной калибровки; гостевые комнаты не должны изменять текущий локальный Elo.

## Исходная архитектура до реализации

В `src/core` правила не зависят от браузера. `src/session/match.ts` содержит `CommandEnvelope` с идентификатором команды, игры, ожидаемой ревизией и стороной, а также `GameSnapshot` и `GameTransport`. Это полезная основа.

До этого этапа `Cabinet` непосредственно использовал локальный `GameSession`, его запись и IndexedDB. Тогда ещё не было сервера, комнат, авторизации мест или настоящего удалённого транспорта. Сейчас добавлены `server/`, `src/online/`, читаемый `GameView` и последовательная сетевая подача в `Cabinet`. Подмена названия режима либо пересылка всего `MatchRecord` не реализуют сеть: запись содержит private RNG и локальные возможности undo/redo.

## Технический выбор

Один TypeScript/Node сервер с HTTP и WebSocket, существующий React/Vite клиент, одна SQLite база на постоянном диске. Начальная эксплуатация — один серверный процесс; распределённый кластер не нужен для комнат с друзьями.

- На сервере — `ws`; в браузере — встроенный WebSocket. Официальный [README ws](https://github.com/websockets/ws) отдельно различает эти среды и показывает HTTP upgrade, аутентификацию и heartbeat.
- Для SQLite — `better-sqlite3` с транзакциями; официальные [документация и требования установки](https://github.com/WiseLibs/better-sqlite3). При установке исполнитель проверяет совместимость с поддерживаемым Node LTS на Mac и в контейнере, фиксирует lockfile. Зависимости сервера не включаются во frontend bundle.
- Production-сервер отдаёт `dist`, HTTP API и `/ws` с одного origin. Для разработки Vite проксирует API/WebSocket на локальный backend. Клиент не содержит захардкоженных `127.0.0.1` или Wi-Fi IP для сетевого соединения.
- Поставка включает Dockerfile, пример окружения, постоянный volume для SQLite, health endpoint и инструкции HTTPS/WSS через reverse proxy. Покупка хостинга, домена и публикация на неизвестный аккаунт не входят в этот этап.

## Сервер определяет игру

Клиент отправляет намерение: ход с выбором превращения, окончание бонусного действия, сдачу либо действие с предложением ничьей. Сервер связывает соединение с местом, проверяет ревизию и легальность через тот же `src/core`, определяет необходимый бросок и сохраняет единственный результат.

Броски онлайн генерируются серверным криптографическим генератором с равномерными гранями 1–6. Будущая случайность не отправляется клиентам. Существующий короткий детерминированный local PRNG полезен для локального undo, но не является источником секретной будущей случайности сетевой партии. Не маскируй серверные броски как `tutorial` или `fixed`: у сети должна быть честная отдельная запись разрешённых действий.

Публичное состояние содержит текущие фигуры и права, память реакций, эффекты, точные сроки, completed-turn serial, бонусного исполнителя, повторения, взятые фигуры, результат и ревизию. Клиент не присылает авторитетную доску, победителя, грань или изменение рейтинга.

Ревизия, действие, разрешённый бросок, события и результат фиксируются одной серверной транзакцией **до подтверждения и рассылки**. Для каждой комнаты команды обрабатываются последовательно. Повтор того же `commandId` с тем же payload возвращает прежний ответ; тот же ID с другим payload отклоняется. После тайм-аута клиент запрашивает состояние и при необходимости повторяет тот же ID. Он не создаёт новый ID для сомнительного старого хода и не получает новый бросок.

Порядок проверки: права места → поиск уже сохранённого ID и сравнение канонического payload → прежний ACK либо ошибка несовпадения → для действительно новой команды проверка ревизии и правил. Нельзя слепо использовать текущий `GameSession.submit`: его локальный dedup не сравнивает actor/payload и не хранит сетевой ACK. `hydrateMatch` также проверяет броски через local `nextDie(rootSeed)`; серверный журнал с криптографическими исходами восстанавливается своим валидируемым форматом через тот же core. Версии протокола, правил и серверной записи явные; несовместимый клиент получает понятное требование обновить страницу.

## Места, приглашения и соединения

Создатель и приглашённый получают разные серверные права на конкретные места. Используй непредсказуемые идентификаторы/токены. Наличие ID комнаты не даёт права ходить любой стороной. Одноразовое приглашение на свободное место обменивается на отдельное право восстановления; приглашение не является вечным секретом владельца.

Гостевую сессию можно хранить в HttpOnly SameSite cookie с Secure в HTTPS. Если выбран иной механизм, кратко обоснуй его и проверь защиту места. Не помещай постоянные seat/resume токены в query URL, историю, консоль, общие логи или snapshot соперника. Чувствительная часть одноразовой ссылки может передаваться во fragment и обмениваться через API. При смене активного соединения того же места старое теряет право отправлять команды; это проверяется сервером, а не только закрытием вкладки.

Гостевая сессия выдаётся до обмена приглашения. Занятие места и расходование invite происходят атомарно с привязкой к этой сессии. Если HTTP-ответ потерян, повтор той же сессии возвращает уже занятое ею место; использованная ссылка не должна запирать законного гостя. Другая сессия по использованному приглашению место не получает.

Один профиль браузера не должен незаметно занимать обе стороны одной комнаты. Для двух независимых игроков в QA нужны разные контексты/браузеры или устройства. Третий игрок получает понятное «Комната занята». Ники ограничиваются по длине и выводятся как текст.

Heartbeat обнаруживает потерю связи. Клиент показывает короткое состояние «Восстанавливаем соединение» и блокирует отправку новых ходов до свежего snapshot. После обновления страницы или возврата телефона приложение восстанавливает своё место, текущую фазу и уже выпавшую грань. Серверный рестарт сохраняет партию и права восстановления в SQLite.

Без часов краткий обрыв не означает поражение. В первом этапе игровые ходы приостанавливаем до подключения обоих; собственная сдача остаётся доступной. Нет фоновых автосдач или побед по сетевой ошибке. Неактивная комната хранится 24 часа с последнего принятого действия/присоединения; heartbeat не продлевает её вечно. Истёкшая незавершённая комната закрывается как технически прекращённая без победы и рейтинга. Это состояние жизненного цикла комнаты, а не выдуманная шахматная ничья в `GameOutcome`. Завершённая партия хранится не меньше семи дней; сроки вынесены в конфигурацию.

## Ходы, согласие на ничью и реванш

Сервер не принимает действие другой стороной, устаревшую ревизию, ход из завершённой партии, незаконный выход из шаха или чужой бонус. Условия REMORSE, включая взятия своих при жажде крови, применяются полностью.

Ничья по соглашению требует двух разных мест: предложение одной стороны и принятие другой. Клиент не может единолично отправить текущую локальную команду `agreeDraw` как разрешение завершить сетевую партию. Предложение привязано к идентификатору; ход, отказ или новое предложение инвалидируют старое принятие. Сдача относится только к своему месту. Повторение проверяет сервер.

После результата оба могут согласиться на реванш. Создаётся новая игра с новым ID, чистой стандартной позицией и поменявшимися цветами; прежний результат остаётся неизменным. Локальный undo в сетевой игре недоступен. Будущая перемотка истории должна быть просмотром, не изменением общей партии.

## Подача событий

У двух клиентов могут отличаться язык, ориентация, 2D/3D, качество, звук и reduced motion. Это не меняет игру. Сервер передаёт упорядоченные события с устойчивыми ID; клиент показывает ход, кубик, эффект фигуры и шах/мат в существующей очереди. У обоих одна грань и одна реакция. Достаточна согласованная последовательность; синхронизация каждого кадра не нужна.

Не ставь авторитетный игровой процесс в зависимость от клиентского `animationDone`: закрытая вкладка не может навечно остановить комнату. Presentation queue локально не позволяет следующему событию визуально обогнать бросок. При reconnect текущий snapshot применяется спокойно: старые броски, звуки и финальные сцены не повторяются. Счётчики правил идут по завершённым ходам, а не по времени сети/анимации.

Раздели последнюю принятую серверную ревизию (`authoritativeRevision`) и показанную (`displayedRevision`). Пока идёт кубик, следующий законный commit может прийти от соперника с reduced motion. Его нельзя отбросить из-за `Cabinet.animating` или немедленно показать вместо текущей сцены. Входящие данные принимаются по порядку, presentation догоняет отдельно, ввод своего нового решения разрешается только на актуальной показанной позиции. Длительно скрытая вкладка может перейти к свежему snapshot без проигрывания всей накопленной очереди. Обязательно проверить два последовательных commit во время первого reveal.

Новый кубик остаётся в информационной панели, доска открыта. Ни уведомление о соединении, ни ожидание соперника не превращаются в постоянный полноэкранный экран поверх позиции. Обязательные действия видны на телефоне без прокрутки документа.

## Граница поставки

Этап считается завершённым, когда два независимых клиента через настоящий сервер играют полную партию, видят одинаковые случайные результаты и восстанавливаются после обрыва и серверного рестарта. Один браузер с двумя табами, общим IndexedDB или BroadcastChannel не доказывает сетевой режим. Доступ по локальной Wi-Fi сети проверяет два устройства; доступ из разных сетей проверяется отдельно после выбора публичного размещения.
