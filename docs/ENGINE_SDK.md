# Chess 2 Engine SDK v1

## Что создано

`src/sdk/` — общее типизированное ядро поиска. Оно не импортирует шахматные фигуры, доску, цвета, правила REMORSE или правила Форсажа. Обе игры используют **один** алгоритм `searchGame`, свои адаптеры правил и свою оценку позиции.

- REMORSE: `src/engine/adapter.ts`; прежняя функция `search` в `src/engine/search.ts` остаётся совместимой с существующими клиентами.
- Форсаж: `src/overdrive/engine/search.ts`.
- Общий протокол Worker: `src/sdk/worker.ts`; обе игры используют `createSearchHandler`.

SDK предназначен для пошаговых игр двух сторон с нулевой суммой и общедоступным состоянием. Случайные исходы поддерживаются. Скрытые карты, одновременный выбор обеих сторон, более двух игроков и обучение нейросети не реализованы. Для Джокера со скрытой рукой потребуется отдельная модель информации и поиска; передача боту серверной колоды не является допустимой адаптацией.

## Контракт игрового модуля

Точные TypeScript-типы находятся в `src/sdk/types.ts`.

| Метод / поле | Что предоставляет игра |
|---|---|
| `id`, `version`, `information` | Идентификатор, версия семантики правил/оценки и явное `perfect` для общедоступного состояния. |
| `player(state)` | Сторону, которая принимает следующее решение. Она не обязана чередоваться после каждой команды. |
| `legalActions(state, probe)` | Все законные действия, включая дополнительные цели и доступные требования ничьей. |
| `outcomes(state, action)` | Неотрицательные вероятности исходов с суммой 1. Для детерминированного хода — один исход с вероятностью 1. |
| `apply(state, action, chance, probe)` | Новое состояние после уже законного действия и выбранного исхода. Входное состояние не изменяется. |
| `terminal(state)` | Победителя либо ничью; проверка мата и других условий принадлежит правилам игры. |
| `evaluate(state, perspective)` | Оценку с точки зрения указанной стороны. Конечное число строго между −500 000 и +500 000. |
| `actionKey(action)` | Устойчивый уникальный ключ полного действия, включая выбранную цель, режим и превращение. |
| `orderActions(state, actions)` | Необязательное ранжирование всех полученных законных действий; приоритет влияет на скорость поиска. |
| `turnsElapsed(before, after)` | Число завершённых ходов. Может быть нулём для дополнительного решения. |
| `canEvaluate(state)` | Можно ли остановить поиск на этой границе глубины; незавершённую составную фазу можно продолжить. |
| `cacheIdentity(state)` | Ключ позиции и отдельный контекст истории для повторений и других зависимых от пути правил. |
| `fallbackScore(...)` | Необязательную оценку законного действия до завершения первого прохода поиска, например 0 для требования ничьей. |

Адаптер обязан включить в идентичность всё, что меняет будущие возможности: сторону, право рокировки, взятие на проходе, энергию, срок усиления, состояние фигур, историю награждённых шахов, повторения и другие счётчики своего варианта. `history` сравнивается через `Object.is`: можно вернуть полный канонический ключ или неизменяемый объект истории. Использование ссылки безопасно, но даёт меньше совпадений, чем полный ключ. Изменять объект истории на месте нельзя.

## Поиск

Алгоритм — expectiminimax с итеративным углублением и alpha-beta на узлах решений. В случайном узле берётся сумма `вероятность × оценка продолжения`. Каждое случайное продолжение получает полное окно поиска: частичная сумма не считается безопасной alpha-beta-границей.

Глубина измеряется завершёнными ходами, определёнными адаптером. REMORSE продолжает рассматривать бонус той же стороны; Форсаж выполняет составной приём как одну атомарную команду. Если следующий игрок остался прежним, поиск продолжает максимизацию для него. Жёсткого переключения знака после любого перемещения нет.

Терминальная победа получает оценку около ±1 000 000 с поправкой на число завершённых ходов: движок предпочитает более раннюю победу и более позднее поражение. Оценка фигур и ресурсов не может случайно превысить этот диапазон.

Таблица транспозиций создаётся заново для каждого запроса, ограничена 8192 записями и использует пространство имён игры/версии. Точное значение повторно используется только при совпадении позиции, истории, остаточной глубины и прошедших ходов. В другом контексте сохранённое действие может служить подсказкой порядка перебора; его оценка не переносится.

Первый законченный проход становится решением. Если следующий проход остановлен временем, лимитом узлов или отменой, сохраняется последний **полностью законченный** проход; данные разной глубины не смешиваются. Если не закончился даже первый, возвращается законное статически ранжированное действие с `depth: 0`. Это не считается рассчитанным на один ход решением.

Бюджет состоит из `maxDepth`, `maxNodes`, `maxTimeMs`, `temperature`. Нулевая температура всегда выбирает лучшую найденную оценку с устойчивым разрешением равенства. Положительная температура допускает взвешенный случайный выбор в пределах трёх температур от лучшего результата. Эти параметры задаёт каждая игра; подписи Elo сами по себе не являются калибровкой.

## Диагностика и ограничения времени

Результат содержит действие, число просмотренных переходов, время, завершённую глубину, оценку и причину остановки. `principalVariation` хранит продолжение с наиболее вероятным исходом каждого случайного узла; вероятность и сам исход записаны явно. Это наглядный пример продолжения, а не предсказание кубика и не весь случайный граф. При статическом запасном решении линия пуста.

Синхронный поиск проверяет время и отмену между переходами; дорогой генератор правил должен вызывать переданный `probe`. Первичный список корневых действий строится полностью для законного запасного решения. Поэтому `maxTimeMs` — кооперативный бюджет, не гарантия прерывания ровно через заданное количество миллисекунд. В браузере жёсткая отмена выполняется завершением Worker. Защита `maxTransitionsPerLine` (по умолчанию 256) останавливает ошибочные бесконечные цепочки команд с нулевой стоимостью хода; диагностируется `transition-limit`.

## Общий Worker

`createSearchHandler` проверяет версии правил, движка и профилей, существование профиля, идентификатор партии/запроса, целые неотрицательные ревизию и поколение сессии; затем вызывает валидатор состояния конкретной игры. Ошибочные данные не запускают поиск. Ответ не содержит исключений или сериализованного игрового состояния.

Клиент сопоставляет все восемь полей идентичности через `matchesSearchIdentity` и отбрасывает запоздалый ответ от старой партии или старого поколения. Эта проверка дополняет отмену Worker и проверку хода общими правилами. Worker не является сервером сетевой партии: её авторитетное состояние проверяется отдельно на сервере.

## Проверка

Тесты SDK находятся в `src/sdk/search.test.ts` и `src/sdk/worker.test.ts`. Они проверяют отдельную игру со снятием камней, минимакс, ожидаемую оценку случайных ветвей, дополнительный ход той же стороны, незавершённую фазу, историю повторений в кэше, сохранение законченного решения при прерывании, ограниченную случайность сложности, протокол Worker и полный перебор с независимым вычислением значений на сгенерированных деревьях.

Существующие тесты REMORSE продолжают вызывать прежний публичный API и теперь проходят через SDK, в том числе бросок после взятия, бонусный ход, жажда крови, ничья по повторению и десять профилей. Проверки специфических способностей, энергии, длительности форм и силы Форсажа находятся в его собственном модуле и отчёте. Итоговые количества и среда запусков фиксируются в общем отчёте приёмки конкретного коммита.

Команда целевой проверки:

```sh
npx vitest run src/sdk src/engine/search.test.ts
```
