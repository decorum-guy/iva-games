# Доступ к состоянию VPS из чата

## Статус и назначение

Подготовлен отдельный канал диагностики через GitHub Actions. Его установка на VPS и настоящий снимок из чата **пока не подтверждены**. Этот документ описывает подготовку и приёмку; состояние сервера узнаётся из нового снимка, а не из исторического отчёта `WAITING_DNS`.

Уже существующий `iva-deploy` доставляет закреплённые выпуски после CI. Его ключ запускает только принятую команду выпуска. Обычный деплой обновляет контейнеры и pins, но не устанавливает новые root-owned помощники. Поэтому диагностику один раз устанавливает локальный агент через существующий административный доступ `ssh iva-games`.

После настройки агент в чате сможет запросить новый снимок повтором отдельного задания Actions и прочитать результат. Прямой интерактивный SSH из этого чата этим не появляется. В текущем наборе инструментов GitHub есть чтение jobs/logs и `rerun_workflow_job`; `workflow_dispatch` не предоставлен, а локальный `gh` в облачной среде не авторизован. Доступность инструментов и права интеграции нужно проверять в каждой новой среде.

## Что разрешено

Новый пользователь `iva-ops` с отдельным ключом запускает только одну операцию без аргументов. Снимок содержит:

- время сбора, состояние активации и код известной причины ожидания или ошибки;
- текущий SHA, закреплённые digest образов, сведения о pending-выпуске;
- состояние фиксированных systemd-сервисов, таймера и трёх контейнеров;
- идентификаторы контейнеров, образов и счётчики перезапусков;
- объём памяти, свободное место и результаты трёх фиксированных HTTPS health-проверок;
- ограниченный список известных событий активации без свободного текста журналов.

Сырые журналы, `.env`, настройки бота, приватные ключи, коды входа, базы, имена игроков и полный `docker inspect` не возвращаются. Поля строятся по разрешённой схеме: неизвестные ключи и сообщения отбрасываются. Вывод повторно фильтруется на runner перед попаданием в Actions. Ограничены длительность команд, размер чтения и размер JSON. Журналы Actions доступны читателям репозитория, поэтому маскировка GitHub Secrets не заменяет эту фильтрацию.

У `iva-ops` нет общего sudo, доступа к Docker socket, PTY, forwarding, загрузки файлов или произвольной команды. Принятый `iva-deploy` сохраняет отдельные права. Диагностика не перезапускает приложения, не меняет DNS, базу, pins, таймер, firewall или SSH-порт. Обычные системные журналы SSH/HTTP могут зарегистрировать само чтение.

## Однократная настройка на Mac и VPS

Работай из проверенного checkout с этими файлами. Сначала прочитай installer и helper; установка root-owned кода требует административной проверки. Не запускай повторно `install-host.sh` и не отключай работающий доступ администратора.

1. Подтверди существующий `ssh iva-games` через `iva-admin` на порту `2233`. Сохрани независимую административную сессию на время установки. IP, пароль root и перенос порта повторно не нужны.
2. На Mac создай отдельный Ed25519-ключ для Actions в приватном временном каталоге (`umask 077`). Это ключ автоматизации без passphrase, ограниченный на сервере одной операцией. Не используй личный ключ Mac или ключ `iva-deploy`. Не печатай приватную часть и не помещай её в checkout.
3. Передай на VPS проверенные `install-ops.sh`, `ops-status`, `ops-status.py`, `iva-ops.sudoers` с сохранением соседства файлов и **только публичную** часть нового ключа. Запиши SHA проверенных исходников. Запусти через администратора:

   ```bash
   sudo bash /absolute/path/to/reviewed/deploy/iva-games/install-ops.sh /absolute/path/to/iva-games-ops.pub
   ```

4. Installer устанавливает root-owned файлы в `/opt/iva-games/ops`, отдельный home `/var/lib/iva-ops`, точное правило `/etc/sudoers.d/iva-ops` и SSH Match для `iva-ops`. Он проверяет `sshd -t`, эффективные политики существующих пользователей и перезагружает конфигурацию только после проверки. Порт, firewall и текущие admin/deploy-ключи остаются прежними. При ошибке не исправляй это ослаблением общих ограничений SSH; исследуй конкретный отказ.
5. Из независимого подключения с новым ключом проверь разрешённый вызов `ssh -T ... iva-ops@HOST` без remote command. Попытки `id`, `sh`, передачи аргументов, SFTP, PTY и forwarding должны быть отклонены. Проверь сохранение доступа `iva-admin` и ограничений `iva-deploy`. Не вызывай настоящий deploy ради проверки доступа.
6. В окружении GitHub **`production`** добавь secret `IVA_OPS_SSH_KEY` через stdin авторизованного `gh`, а не через аргумент с содержимым ключа. Используются существующие variables `IVA_SSH_HOST`, `IVA_SSH_PORT`, `IVA_SSH_HOST_KEY`. Проверенный host key берётся из действующего доступа; один лишь непроверенный `ssh-keyscan` не устанавливает доверие.

   ```bash
   gh secret set IVA_OPS_SSH_KEY --repo decorum-guy/iva-games --env production < "$ops_private_key_file"
   gh variable set IVA_OPS_ENABLED --repo decorum-guy/iva-games --env production --body true
   ```

   Здесь `ops_private_key_file` — путь к созданному приватному файлу, а не содержимое ключа. Включай variable только после успешной установки и проверки. Удаляй временную копию приватного ключа после настройки; для отзыва или ротации замени отдельный ключ и secret. Не копируй его в отчёты, GitHub artifacts или сообщения.

7. Доведи проверенный PR до `main` обычным порядком проекта, сохраняя обязательные CI. Файл `iva-server-status.yml` должен присутствовать в default branch. Никакие соседние PR не включаются автоматически. Затем создай исходный запуск с Mac:

   ```bash
   gh workflow run iva-server-status.yml --repo decorum-guy/iva-games --ref main
   gh run list --repo decorum-guy/iva-games --workflow iva-server-status.yml --branch main --limit 5 --json databaseId,headSha,createdAt,event,status,conclusion
   ```

   Для выбранного run получи job ID и проверь результат:

   ```bash
   gh run view "$ops_run_id" --repo decorum-guy/iva-games --json jobs
   gh run view "$ops_run_id" --repo decorum-guy/iva-games --log
   ```

   Передай в чат URL run, числовой **job ID**, SHA и `collected_at`. Секреты и raw SSH output передавать не нужно. Финальная проверка доступа из чата — настоящий повтор этого job и чтение нового снимка с новым временем сбора.

## Как устроен запуск

Workflow **Iva Games server snapshot** (`.github/workflows/iva-server-status.yml`) содержит только один job `Read server snapshot`. В нём нет deploy, backup или зависимых команд изменения сервера. Он работает только с доверенным `main` и `production`; pull request не исполняется с диагностическим ключом.

У environment задано `deployment: false`: чтение использует его secrets/variables, но не создаёт запись о выпуске. Если в будущем у окружения появятся несовместимые custom deployment protection rules, согласуй отдельное диагностическое окружение с теми же ограничениями ветки; не ослабляй production ради чтения. [Описание GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/deploy-to-environment).

Первый запуск создаётся вручную через локальный `gh workflow run` или GitHub UI. После успешных основных выпусков **Iva Games release images** workflow автоматически создаёт новый исходный снимок. PR-проверки образов и ручной build-only запуск release не дают такого доступа. Cron и периодические уведомления здесь не добавлены.

Пока `IVA_OPS_ENABLED` не равно `true`, workflow сообщает об отсутствии настройки и не подключается к серверу. Зелёный run с этим сообщением не доказывает доступ. При включённом флаге отсутствие ключа или SSH-конфигурации — ошибка. Успешный сбор снимка означает успешное чтение: приложение внутри него всё ещё может быть нездоровым или ждать DNS.

Повтор job использует исходные SHA/ref и права первоначального исполнителя. GitHub допускает повтор в пределах **30 дней** после первого запуска и не более **50 повторов** одного run. После истечения срока, исчерпания повторов или изменения схемы helper нужен свежий исходный запуск. Для этого служат следующие обычные выпуски или ручной dispatch с Mac. Повтор старого job не является способом применить новый workflow-код.

Для повторов интеграции GitHub нужно разрешение **Actions: write** на этот репозиторий. Наличие возможности редактировать файлы не доказывает это право. Его можно проверить на отдельном PR workflow **Iva Games server access checks**: он не содержит production secrets и не запускает выпуск. После установки всё равно требуется отдельная проверка живого snapshot job. При отказе интеграции не извлекай токены из сессий и не расширяй серверный ключ до shell: зафиксируй недостающее разрешение.

## Приёмка и отзыв

В отчёте укажи отдельно: локальные тесты helper, успешную установку, разрешённые/запрещённые SSH-операции, первый run и повтор из чата, фактическое состояние приложений. Сопоставь snapshot с чтением администратором; подтвердить одни только CI-тесты недостаточно. Не сохраняй raw конфигурацию или данные пользователей.

Для прекращения запусков установи `IVA_OPS_ENABLED=false`. Для отзыва доступа удали secret и установленный public key `iva-ops` через администратора. Остальной доступ и деплой продолжат использовать свои ключи. Изменение allowlist, добавление команд restart/rollback или доступа к базе требует отдельной реализации и проверки; этот пакет их не разрешает.

Официальные ограничения GitHub: [повтор workflow и jobs](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs), [REST API для повторов](https://docs.github.com/en/rest/actions/workflow-runs#re-run-a-job-from-a-workflow-run), [ручной запуск workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).
