# Iva Games — Telegram-привязка и доставка приглашений v1

Дата: 25 ноября 2026 года. **Статус: спецификация предлагаемого поведения, не реализованная интеграция и не отчёт о живой проверке.** В рамках подготовки этого документа бот не создавался, webhook не настраивался, сообщения и приглашения никому не отправлялись.

Основание — прямой сценарий владельца: вход на сайт → «Подключить TG-бота» → deep link с кодом → `/start` в боте → привязка к учётной записи → новые приглашения на игры приходят туда. Ниже этот сценарий дополнен явным подтверждением в исходном браузере, чтобы пересылка ссылки сама по себе не привязывала чужой Telegram.

Общие аккаунты, комнаты и приглашения описаны в [PLATFORM_V1.md](PLATFORM_V1.md). Telegram здесь — дополнительный канал доставки. Он не заменяет вход на сайт, не создаёт аккаунты, дружбу или игровые места.

## 1. Проверенные ограничения Telegram

Официальные документы проверены при подготовке спецификации. Приведены только ограничения, от которых зависит проект; остальные значения сроков и лимитов ниже — решения Iva Games.

| Факт внешнего API | Применение |
|---|---|
| Bot deep link имеет вид `https://t.me/<bot_username>?start=<payload>`; payload до 64 символов из `A-Z`, `a-z`, `0-9`, `_`, `-` | Использовать короткий opaque token, а не JSON или JWT с данными аккаунта |
| В приватном чате нажатие Start передаёт боту `/start <payload>` | Сам переход по ссылке ещё не является завершённой привязкой |
| User ID и Chat ID — числовые идентификаторы; могут выходить за 32 бита | Хранить числовую идентичность, а не mutable username |
| Webhook поддерживает секрет в `X-Telegram-Bot-Api-Secret-Token`, возможна повторная доставка update | Проверять секрет и дедуплицировать update до побочных действий |
| `sendMessage` возвращает Message при успехе; на flood control может прийти `retry_after` | Различать ответ API, неизвестный исход и чтение пользователем |

Источники: [Deep Linking](https://core.telegram.org/bots/features#deep-linking), [Bot links / Start](https://core.telegram.org/api/links#bot-links), [User](https://core.telegram.org/bots/api#user), [Chat](https://core.telegram.org/bots/api#chat), [Update](https://core.telegram.org/bots/api#update), [setWebhook](https://core.telegram.org/bots/api#setwebhook), [sendMessage](https://core.telegram.org/bots/api#sendmessage), [ResponseParameters](https://core.telegram.org/bots/api#responseparameters).

В v1 единственный разрешённый путь первоначального подключения — пользователь сам открывает личный чат и отправляет `/start`. Проект не использует альтернативные возможности приглашения владельцем бота, business/guest-сценарии или добавление в группу для получения права на рассылку. Это наша продуктовая политика, а не абсолютное утверждение обо всех возможностях Telegram.

## 2. Владельцы данных и минимальный scope

Telegram-адаптер — server-only модуль `apps/platform`. Он обрабатывает доверенные входящие update и доставляет разрешённые события из outbox. Токен бота не попадает в клиентские сборки, репозиторий или логи. Для development и production — разные bot identity и секреты; один production-бот обслуживается одним владельцем webhook.

В v1 отправляются только:

- ответы на явные команды пользователя: начало/ошибка привязки, состояние и управление доставкой;
- уведомления о приглашениях, **явно созданных другим пользователем на сайте**, если получатель уже завершил привязку и отдельно включил этот канал.

Подключение и `/start` не рассылают старые приглашения, не создают тестовую игру, не зовут друзей и не включают расписание. Автоматические напоминания, анонсы релизов, дайджесты и «пригласить всех» вне scope.

## 3. Данные и инварианты

### `telegram_link_attempts`

`attemptId`, `playerId`, `initiatingWebSessionId`, `tokenHash`, `state`, `createdAt`, `expiresAt`, `candidateTelegramUserId`, `candidateChatId`, `candidateDisplaySnapshot`, `proofCodeHash`, `proofFailures`, `consumedAt`.

Состояния: `issued -> awaiting_web_confirmation -> confirmed`; из незавершённых состояний возможны `expired`, `cancelled`, `rejected`. Один активный attempt на игрока. Создание нового атомарно отменяет прежний. Истёкший/использованный token никогда не восстанавливается.

### `telegram_bindings`

`bindingId`, `playerId`, `botId`, `telegramUserId`, `privateChatId`, `bindingVersion`, `status`, `notificationsEnabled`, `consentedAt`, `linkedAt`, `revokedAt`, `lastDeliveryError`.

Ограничения: не более одной активной привязки на `playerId` и одной на `(botId, telegramUserId)`. `telegramUserId` и `privateChatId` — разные поля; identity берётся из `message.from.id`, destination из `message.chat.id`. В SQLite использовать 64-bit integer; в JSON границах проекта — десятичную строку, чтобы не зависеть от неявных преобразований JS/ORM. Имя и `@username` только для отображения, они не доказывают идентичность.

`status`: `active`, `unreachable`, `revoked`. Mute — `notificationsEnabled=false`, а не потеря связи с аккаунтом. Unreachable не освобождает Telegram ID для чужого аккаунта: уникальные ограничения применяются ко всем неотозванным связям, включая active и unreachable. Повторное подключение той же пары не должно создавать вторую строку или новую подписку.

## 4. Полный сценарий привязки

### Шаг A. Вход и запрос на сайте

Пользователь должен иметь подтверждённый email, активную web-session и недавнюю проверку пароля (не старше 10 минут). Он нажимает «Подключить Telegram»; сервер проверяет CSRF и создаёт attempt.

Token: **32 байта из CSPRNG**, base64url без padding. С префиксом `l1_` payload имеет 46 символов и укладывается в ограничение Telegram. Он не кодирует playerId, email, username или права. В базе только `SHA-256(token)`; для высокоэнтропийного случайного токена это не схема хеширования паролей. TTL — 10 минут, по серверному времени.

Пример формы ссылки, не действующий токен:

```text
https://t.me/<configured_bot_username>?start=l1_<opaque_random_token>
```

Ответ сайту содержит ссылку, `attemptId` и срок; он `Cache-Control: no-store`. UI не передаёт ссылку сторонней аналитике и предлагает не пересылать её. В access/application логах query и payload редактируются. Cookie и web-session ID не включаются в deep link.

### Шаг B. `/start` в личном чате

Доверенный webhook должен содержать обычное `message` с `chat.type=private`, `message.from` и `from.is_bot=false`. Группы, каналы, guest/business update, callback от другого сценария и пересланное сообщение не подтверждают привязку. `/start` без token показывает только инструкцию открыть настройки сайта; не раскрывает наличие чужой учётной записи.

В транзакции сервер находит хеш token, проверяет `state=issued`, срок и активность исходной web-session. Затем **однократно закрепляет** candidateTelegramUserId/privateChatId и переводит attempt в `awaiting_web_confirmation`. Второй `/start` не может заменить кандидата. Повтор того же update/того же пользователя возвращает прежнее безопасное состояние; другой пользователь получает нейтральную ошибку.

После этого бот сообщает, что требуется подтверждение на сайте, и выдаёт короткий proof-код (8 случайных символов base32). Код показывается **только в этом личном чате**, для проверки на сервере сохраняется его хеш; максимум 5 попыток ввода и общий оставшийся TTL attempt. Для восстановления после сбоя служебный ответ с кодом записывается в outbox в той же транзакции, что и candidate: секретный payload шифруется поддерживаемой библиотекой с серверным ключом вне базы и удаляется после доставки/истечения TTL. Его plaintext не сохраняется в журнале событий, логах или длительной истории уведомлений. Повтор update не генерирует другой код и не меняет candidate. Код не является логином в Iva Games. Сообщение не содержит email или других данных аккаунта.

Для служебного ответа уникальный outbox-key связан с attempt, а expiry равен оставшемуся сроку attempt. Перед каждой попыткой worker проверяет, что attempt всё ещё awaiting_web_confirmation, его исходная web-session действительна и TTL не истёк; отмена/новый attempt/завершение прекращают старую очередь и удаляют секретный payload. До подтверждённого ответа Bot API worker может повторить тот же зашифрованный payload, в том числе при неизвестном исходе; возможен дубль того же кода. После состояния `sent` payload удаляется, а повтор `/start` показывает только статус ожидания и не пытается восстановить код из хеша. Если пользователь потерял уже отправленное сообщение, он отменяет попытку на сайте и начинает новую. После `confirmed` payload считается использованным: повтор не создаёт связь и не выдаёт новые полномочия; идемпотентный повтор web-confirm лишь возвращает результат той же завершённой операции.

### Шаг C. Подтверждение в исходной web-session

Страница настроек через authenticated API получает статус attempt. Сервер возвращает только masked candidate identity: частично скрытое имя/username при наличии и последние 4 цифры numeric ID. Полный ID не нужен клиенту. Пользователь видит пояснение «Подключается этот Telegram» и вводит proof-код из личного чата.

Подтверждение — отдельный POST. Сервер проверяет **ту же исходную web-session**, того же playerId, недавнюю reauthentication, CSRF, TTL, candidate и код. Новый браузер/сессия не может завершить старый attempt: нужно начать заново. Поэтому получатель пересланного deep link, даже отправив `/start`, не может сам завершить binding. Владелец сайта должен отклонить незнакомую identity; протокол не обещает защиты от сознательной передачи своей web-session и кода другому человеку.

На этом же экране отдельный незаполненный заранее checkbox: «Получать новые приглашения на игры в Telegram». Пользователь может привязать Telegram без включения доставки. Сервер хранит выбранное значение и время согласия.

### Шаг D. Фиксация

Одна SQLite-транзакция ещё раз проверяет уникальности, создаёт/подтверждает binding, фиксирует consent и помечает attempt `confirmed`. Token и proof становятся непригодными. Завершённый attempt не выдаёт новую web-session и не меняет пароль.

Сайт показывает завершённую привязку и настройку доставки. Бот может отправить одно служебное подтверждение этой явной операции; потеря ответа не отменяет сохранённую привязку. **Никаких приглашений в качестве проверки не создаётся и не отправляется.**

## 5. Конфликты, перепривязка и отключение

| Ситуация | Поведение v1 |
|---|---|
| Token истёк/отозван/использован | Нейтральная ошибка; новую ссылку создаёт сайт |
| Token использовал другой Telegram | Кандидат не перезаписывается; владелец отменяет attempt и создаёт новый |
| Тот же Telegram уже связан с тем же playerId | Идемпотентно показать действующую связь; delivery consent не включать автоматически |
| Telegram связан с другим аккаунтом | Конфликт, без раскрытия другого аккаунта; автоматического переноса нет |
| У playerId уже другой Telegram | Сначала явная перепривязка с reauthentication; прежняя связь остаётся до успешной проверки новой |
| Успешная перепривязка | Атомарно отозвать старую, увеличить bindingVersion, отменить ожидающие доставки старой версии; новое согласие отдельно |
| Бот заблокирован/доставка запрещена | Binding `unreachable`, отправки прекращаются; сайт остаётся рабочим |
| Mute | Отключить notifications, отменить ожидающие отправки; binding сохранён |
| Unlink | Отозвать binding, attempts и будущие отправки; аккаунт/друзья/игры сохранены |

Unlink на сайте требует reauthentication. В боте `/unlink` требует второй явной кнопки-подтверждения с одноразовым callback nonce, связанным с текущим numeric user ID, private chat и bindingVersion; чужой callback не действует. `/stop` или `/mute` немедленно отключает доставку. `/resume` может включить её только для уже подтверждённой собственной связи и после явного согласия; обычный `/start` не снимает mute.

Unlink отменяет ещё не отправленные записи. Сообщение, уже принятое Telegram или находившееся в сетевом вызове в момент отключения, отозвать гарантированно нельзя; интерфейс не должен обещать обратное. После новой привязки старый outbox не перенаправляется в новый чат.

## 6. Webhook и обработка update

Один уникальный production webhook для данной bot identity, секрет отдельный от bot token и от секретов development. Не подключать этот токен к другому боту или к общей автоматизации уведомлений. `getUpdates` и webhook не используются одновременно.

На входе HTTPS endpoint:

1. Проверить `X-Telegram-Bot-Api-Secret-Token` сравнением с настроенным секретом, ограничение размера body и JSON schema. Неверный секрет — отказ до любых изменений.
2. Проверить разрешённый тип update; неизвестный тип безопасно проигнорировать. Не считать `chat.id`, username, callback text или номер update авторизацией сами по себе.
3. Сохранить запись inbox с уникальным `(botId, update_id)` и необходимые данные в SQLite. После durable commit вернуть 2xx, затем выполнить идемпотентную обработку/служебный ответ. Повтор update не повторяет mutation.
4. Обработчик доверяет numeric identity только из проверенного update. Он заново проверяет ownership каждого attempt/binding/callback, состояние и срок.

Webhook-secret доказывает принадлежность запроса настроенному endpoint; он **не** означает, что конкретный Telegram-пользователь залогинен на сайте. Общий чат и нахождение людей в одной группе также не связывают их аккаунты.

Для минимального набора commands достаточно `message`, необходимых `callback_query` и `my_chat_member` для статуса доступности; настроить `allowed_updates`. Условия доставки всё равно проверяются перед отправкой, так как служебный update может запоздать. Не полагаться на непрерывность update_id и не отбрасывать update только потому, что уже пришёл больший номер. Логи содержат ID операции и категорию ошибки, не link/proof/bot tokens и не полный текст приватной переписки.

## 7. Доставка приглашений через outbox

### Создание события

В одной транзакции сайта создаются приглашение и `notificationEventId`. Telegram delivery row создаётся только если на этот момент получатель имеет `active` binding и `notificationsEnabled=true`. В ней фиксируются `bindingId`, **bindingVersion**, invitationId, получатель и срок актуальности. Уникальный ключ `(notificationEventId, channel, bindingVersion)` предотвращает повторную постановку одного события.

Перед отправкой worker повторно проверяет:

- приглашение всё ещё адресовано этому игроку, `pending`, не просрочено и не отозвано;
- room ещё lobby, актуальны права и нет новой блокировки;
- binding/version/chat не изменились, consent действует, mute/unreachable отсутствуют.

Если приглашение уже принято/отклонено, комната закрыта или привязка изменилась, доставка помечается `skipped`, без новой отправки. При текущей полной комнате допустимо также пропустить запоздавшую доставку с `reason=room_full`; само приглашение остаётся на сайте.

Сообщение содержит имя пригласившего, игру, нейтральную информацию о комнате и кнопку **«Открыть приглашение»** с canonical website URL. Упоминание в Telegram не занимает место и не принимает приглашение. Пользовательский текст экранируется; произвольный Markdown/HTML/URL не передаётся в Bot API как разметка. Email и секретные игровые данные не включаются.

### Состояния и гарантии

`queued -> leased/sending -> sent | retry_wait | delivery_unknown | permanent_failure | skipped`.

Успешный ответ `sendMessage` позволяет сохранить Telegram message_id и обозначить **«Передано Telegram»**. Он не доказывает получение push, чтение или вход пользователя. `accepted`/`joined` берутся только из сайта и runtime, не из успешной доставки.

Локальная дедупликация не создаёт exactly-once гарантию у Telegram. Возможен случай: Telegram принял сообщение, но HTTP-ответ потерян либо процесс упал до сохранения результата. Тогда исход `delivery_unknown`; повтор может дать дубль. В v1 выбрать **at-least-once стратегию попыток в пределах срока актуальности**, честно допуская такой дубль. Это не обещание гарантированной доставки: постоянная ошибка, отключение и истечение срока прекращают попытки.

Предлагаемая политика: не более 5 попыток, backoff с jitter и соблюдением `retry_after`; ни одной попытки после срока приглашения. `429` — повтор по указанной задержке; сетевой timeout/5xx — неизвестный или временный исход; постоянный запрет записи/заблокированный бот — `unreachable` без бесконечного повтора. После перезапуска просроченный lease возвращается в обработку с учётом возможного неизвестного исхода.

При retry не создавать новое invitationId или новый notificationEventId. Дубли одного уведомления ведут на одно приглашение и не обходят атомарную вместимость. Для уже известного message_id можно впоследствии обновить его текст, но редактирование сообщений и подтверждения прочтения не входят в v1.

## 8. Минимальный API и ошибки

| Endpoint / действие | Требуемая проверка |
|---|---|
| `POST /api/me/telegram/link-attempts` | Login, verified email, reauthentication, CSRF; отмена прошлого attempt |
| `GET /api/me/telegram/link-attempts/:id` | Тот же player и исходная web-session; только masked candidate |
| `POST .../:id/confirm` | Тот же session, CSRF, TTL, proof code, уникальности, явный opt-in |
| `POST .../:id/cancel` | Владелец исходного attempt |
| `PATCH /api/me/telegram/preferences` | Login, CSRF, собственная действующая связь |
| `DELETE /api/me/telegram/binding` | Login, CSRF, reauthentication; отмена pending delivery |
| `POST /integrations/telegram/webhook` | Secret, schema, inbox dedupe; без браузерной cookie |

Коды для UI: `LINK_EXPIRED`, `LINK_ALREADY_USED`, `LINK_SESSION_MISMATCH`, `LINK_PROOF_INVALID`, `LINK_PROOF_LOCKED`, `TELEGRAM_ALREADY_LINKED`, `REAUTH_REQUIRED`, `TELEGRAM_UNREACHABLE`. Они не включают сведения о другом владельце. Повтор успешного confirm той же операции возвращает сохранённый результат, но не создаёт дополнительную связь или уведомления.

## 9. Приёмка и границы тестирования

Ни один пункт ниже ещё не отмечен выполненным. Автоматические тесты по умолчанию используют fake Bot API transport и фиксированный тестовый inbox; production token в них недоступен. Live-проверка допускается только отдельным явно разрешённым действием владельца, в известном личном чате и с конкретным текстом. Запуск тестов или всего dev-сервера сам по себе не является разрешением отправить сообщение.

- Обычный сценарий: сайт → deep link → private `/start` → masked identity + proof в исходной web-session → confirmation. Появляется одна binding, invitation не создаётся.
- Доставка остаётся выключенной без checkbox. `/start`, повтор update, обычный login и новая привязка не присылают старые приглашения.
- Пересланная ссылка: другой Telegram может стать кандидатом, но без исходной web-session не завершает binding; владелец отменяет попытку. Чужой кандидат не подменяет уже закреплённого.
- Истёкший token, повтор token, 6-й неправильный proof, другая web-session, group `/start`, forged webhook и подмена username не создают связь.
- Две конкурентные попытки связать один Telegram с разными playerId дают максимум одну активную связь; прежняя связь не перезаписывается автоматически.
- Website-only invitation появляется и работает при отключённом Telegram; успешная отправка не меняет его на accepted/joined.
- Repeated update, повтор enqueue, рестарт после claim и timeout после успешного приёма Bot API не создают второе приглашение. Неизвестный delivery outcome отображается честно; потенциальный дубль уведомления не объявляется невозможным.
- Mute/unlink/block/relink отменяют ещё не начатые отправки; событие старой bindingVersion не уходит в новый чат. Уже отправленное сообщение не считается гарантированно отозванным.
- Telegram `403`, `429`, `5xx` и сетевые ошибки проверены через transport fixture; ретраи ограничены, `retry_after` соблюдается, устаревшее приглашение не отправляется.
- Invite URL не содержит идентичность или credential; после пересылки требует login адресата. Секреты не попадают в access logs, UI errors, аналитику и клиентский bundle.

После реализации отдельно зафиксировать фактические проверки кода и, только при наличии разрешения и реального выполнения, результат live-сценария. Этот документ сам по себе не даёт права регистрировать бота, включать webhook или делать внешние отправки.
