# Первый выпуск на iva-games.pro

Основание: владелец сообщил о покупке **iva-games.pro**. Ни DNS, ни выбранный сервер, ни публичный HTTPS этим сообщением не подтверждены. Этот документ и `deploy/iva-games/` — подготовка конкретного выпуска. Они не означают, что приложения уже опубликованы.

Пакет подготовлен на объединённом коде платформенной приёмки PR #7 (`b7ca237`) и энергетических правил Форсажа PR #8 (`32c1377`). Перед выпуском использовать полный SHA окончательной проверенной интеграции, включая последующие исправления. Исторические числа тестов в отчётах относятся к своим снимкам.

## 1. Два приложения, один вход

Предлагаемая конфигурация сохраняет текущие пути ресурсов, API и WebSocket:

| Публичный адрес | Сервис | Что открывается |
|---|---|---|
| `https://iva-games.pro/` | `platform:4310` | Портал, аккаунты, друзья, комнаты и сайт-приглашения |
| `https://iva-games.pro/api/platform/v1/...` | тот же `platform` | API портала |
| `https://iva-games.pro/integrations/telegram/webhook` | тот же `platform` | Webhook выделенного бота, когда интеграция включена |
| `https://chess.iva-games.pro/` | `chess:4173` | REMORSE |
| `https://chess.iva-games.pro/overdrive/` | тот же `chess` | Форсаж |

Один шахматный контейнер обслуживает обе игры, `/api/health`, `/api/overdrive/health`, `/ws` и `/overdrive-online`. Его обновление затрагивает обе игры. Портал обновляется отдельно; контейнер шахмат при этом не пересоздаётся. Внутренние порты 4173 и 4310 наружу не публикуются. Caddy принимает только публичные 80/443 и передаёт исходные Host, пути и WebSocket.

Новая конфигурация находится в `deploy/iva-games/Caddyfile`. Старый `deploy/Caddyfile` для `remorse.chess-2.online` сохранён. Если на выбранном сервере уже работает reverse proxy, нельзя запускать второй на занятых 80/443: сначала добавить эти два сайта в существующую конфигурацию и проверить доступность upstream из его сети. Данный Compose рассчитан на отдельный экземпляр Caddy; не заменять им действующую конфигурацию остальных сайтов.

Общие аккаунты пока не подключены к гостевым комнатам шахмат. Публикация двух адресов не создаёт этот адаптер. В каталоге у шахмат есть отдельные ссылки «Открыть» / “Play”, над формой входа — гостевые ссылки на обе игры. Они не требуют подтверждения почты и не создают платформенную комнату. Backend-статус шахмат для общих комнат остаётся `unavailable`. Район и Гавань остаются проектами игр; «Пробный стол» не является их реализацией.

Адреса ссылок задаются при сборке портала через `VITE_REMORSE_URL` и `VITE_OVERDRIVE_URL`. Production и `Dockerfile.platform` по умолчанию используют два адреса из таблицы; dev — `http://127.0.0.1:4173/` и `http://127.0.0.1:4185/overdrive/`. Для локальной **production-сборки** установить локальные адреса явно, например:

```bash
VITE_REMORSE_URL=http://127.0.0.1:4173/ VITE_OVERDRIVE_URL=http://127.0.0.1:4185/overdrive/ npm run build:portal
```

При ином размещении Docker принимает те же значения через `--build-arg`. Это публичные ссылки, не секреты. После сборки изменение runtime env их не меняет: нужен новый образ портала. Действующие локальные серверы эта конфигурация не запускает и не останавливает.

Локальные сохранения, рейтинг и гостевые cookie привязаны к origin браузера. Новый домен не переносит автоматически данные с `127.0.0.1` или старого домена. Старые адреса/серверы не выключать и не перенаправлять без отдельного плана; серверные базы также не заменять демонстрационными.

## 2. Образы и постоянные данные

| Образ | Dockerfile | Постоянный volume | Файлы в `/data` |
|---|---|---|---|
| `iva-games-chess:<полный SHA>` | корневой `Dockerfile` | `iva-games-chess-data` | `remorse.sqlite`, `overdrive.sqlite` и их WAL/SHM |
| `iva-games-platform:<полный SHA>` | `Dockerfile.platform` | `iva-games-platform-data` | `platform.sqlite`, `platform-lab.sqlite` и их WAL/SHM |
| Caddy с записанным digest | официальный образ Caddy | `iva-games-caddy-data`, `iva-games-caddy-config` | сертификаты и служебная конфигурация |

У каждого приложения один владеющий процесс. Не запускать несколько реплик поверх этих SQLite-файлов. Volumes внешние для Compose: их создают один раз, отсутствие указанного volume является ошибкой. Обновление приложения не создаёт чистую базу взамен старой. Имена volumes в `release.env` должны оставаться прежними при обычном обновлении.

Оба Dockerfile копируют все восемь workspace-манифестов перед `npm ci`. Корневой образ собирает шахматы, отдельный образ — API и статический портал. В runtime переносятся сборки и production-зависимости. Приложения работают от `node`; `/data` имеет соответствующего владельца. `.dockerignore` исключает локальные базы, `.runtime`, почту, credentials, env-файлы, QA и результаты сборок из build context. Private env-файлы и резервные копии всё равно хранятся вне checkout.

## 3. Подготовить конфигурацию на выбранном сервере

Требуются Docker Engine и **Docker Compose 2.30+**: `env_file.format: raw` передаёт пароль буквально, включая `$`. Секреты задаются как `KEY=value`, без shell-кавычек и подстановок. `release.env` содержит пути и имена образов; `platform.env` — приватные SMTP/Telegram значения. Скрипты не выполняют эти файлы как shell-код.

Пример подготовки каталогов для выделенного Linux-сервера; команды выполняет локальный исполнитель, когда сервер действительно выбран:

```bash
sudo install -d -m 700 /etc/iva-games /srv/iva-games-backups
sudo install -m 600 deploy/iva-games/release.env.example /etc/iva-games/release.env
sudo install -m 600 deploy/iva-games/platform.env.example /etc/iva-games/platform.env
sudoedit /etc/iva-games/release.env /etc/iva-games/platform.env
```

Не выполнять `install` поверх уже заполненных файлов при следующих выпусках. Пользователь, запускающий Compose, должен иметь разрешённый доступ к Docker и чтению этих двух файлов. Если это root, далее выполнять команды в соответствующей административной сессии. Другой путь задаётся через `IVA_RELEASE_ENV=/absolute/path/release.env`; путь к приватному файлу внутри него тоже абсолютный. Не печатать результат обычного `compose config` в общий отчёт: он раскрывает environment. Для проверки использовать `config --quiet`.

### Почта: обязательна для рабочего входа

| Переменная | Значение |
|---|---|
| `SMTP_HOST` | Реальный SMTP-хост выбранного провайдера |
| `SMTP_PORT`, `SMTP_SECURE` | Обычно `465` / `true`; либо поддерживаемые провайдером `587` / `false` с обязательным STARTTLS |
| `SMTP_FROM` | Разрешённый провайдером адрес отправителя, например адрес под доменом владельца |
| `SMTP_USER`, `SMTP_PASSWORD` | Реквизиты этого SMTP, когда требуется авторизация |

В шаблоне отсутствуют выдуманные рабочие реквизиты. Пустые `SMTP_HOST`/`SMTP_FROM` останавливают production startup. `MAIL_MODE=smtp` установлен в Compose; файловая почта в production запрещена самим приложением. Не обходить эту проверку фиктивным SMTP или отключением TLS. Настройки SPF/DKIM/другие записи берутся у выбранного почтового провайдера, не из примерного доменного шаблона.

### Telegram: явное включение после подготовки

По умолчанию `TELEGRAM_ENABLED=false`; сайт-приглашения при этом работают. Для включения нужны все значения:

- `TELEGRAM_BOT_TOKEN`: токен **выделенного** бота Iva Games.
- `TELEGRAM_BOT_USERNAME`: имя без `@`.
- `TELEGRAM_WEBHOOK_SECRET`: отдельный случайный секрет, 32–256 символов `A–Z a–z 0–9 _ -`.
- `TELEGRAM_PROOF_KEY_BASE64`: постоянный случайный ключ ровно 32 байта в обычной Base64. Хранить вместе с резервной конфигурацией, не менять при каждом выпуске.
- `TELEGRAM_PROXY_URL`: проверенный из контейнера маршрут через `kz-bot`, в формате `socks5h://...`, `http://...` или `https://...`. Если нужны логин/пароль, это также секреты. Имя SSH alias само по себе не является DNS-именем внутри нового контейнера.

В актуальном [локальном отчёте](VALIDATION_LOCAL_PLATFORM_2026_11_25.md) от 26 ноября SSH с Mac уже прошёл; из существующего контейнера на `ha-vps` подтверждены SOCKS5 CONNECT через `kz-bot:1080`, проверка TLS и HTTP-ответ Telegram без токена и отправки сообщений. Это не проверка маршрута нового контейнера и не активация нашего бота. Старое описание SSH-зависания внизу отчёта историческое.

Перед активацией локально выполнить `npm run check:kz-bot`; отдельно проверить исходящий proxy route из фактического production окружения. Не копировать токен или пароль соседнего сервиса и не добавлять прямой fallback. Приложение откажется запускаться с `TELEGRAM_ENABLED=true` и неполной/некорректной конфигурацией.

Приложение **не регистрирует webhook автоматически**. После готовности HTTPS отдельно зарегистрировать у выделенного бота endpoint `https://iva-games.pro/integrations/telegram/webhook`, тот же `secret_token` и только нужные `allowed_updates`: `message`, `callback_query`, `my_chat_member`; запрос Bot API также проходит через согласованный прокси. Не помещать токен в командную строку, историю или access log. Убедиться, что другой процесс не использует этот токен через polling. Реальный link/invite-сценарий проводить только с согласованным получателем; обычные проверки не отправляют реальных сообщений.

## 4. Собрать и проверить точный кандидат

Сборка выполняется из чистого checkout проверенного итогового SHA на сервере или builder с архитектурой целевого сервера. Команды не публикуют сайт:

```bash
git status --short
release_sha="$(git rev-parse HEAD)"
docker build --pull --build-arg VCS_REF="$release_sha" -f Dockerfile -t "iva-games-chess:$release_sha" .
docker build --pull --build-arg VCS_REF="$release_sha" -f Dockerfile.platform -t "iva-games-platform:$release_sha" .
docker pull caddy:2
docker image inspect caddy:2 --format '{{index .RepoDigests 0}}'
```

Записать оба полных тега в `CHESS_IMAGE` и `PLATFORM_IMAGE`, а **полученный** digest Caddy — в `CADDY_IMAGE`. Не пересобирать разные исходники под прежним тегом. Сохранить вывод ID/digest образов и SHA в приватной записи выпуска. `node:24-bookworm-slim` — обновляемый базовый тег; повторная сборка в другой день может получить другой образ. Для отката хранить именно уже проверенный образ, а для переноса между машинами использовать registry digest или `docker save`/`docker load` этого образа.

На чистом первом размещении создать volumes один раз:

```bash
docker volume create iva-games-chess-data
docker volume create iva-games-platform-data
docker volume create iva-games-caddy-data
docker volume create iva-games-caddy-config
deploy/iva-games/compose.sh config --quiet
deploy/iva-games/compose.sh run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
```

Если уже есть настоящие серверные базы, это **миграция**, а не чистый старт: сделать согласованную копию, проверить её и перенести в новые volumes до первого запуска. Не выдавать создание пустых volumes за сохранение существующих пользователей. Локальные демонстрационные credentials/партии не импортировать в публичный сервис.

Сверить фактические имена исходных файлов: старый шахматный сервер без `OVERDRIVE_DATABASE_PATH` использует `${DATABASE_PATH}.overdrive.sqlite`, например `remorse.sqlite.overdrive.sqlite`. Новый шаблон явно задаёт `overdrive.sqlite`; автоматического поиска/переименования нет. При миграции подготовить согласованные SQLite-копии под именами из таблицы (через backup API либо после чистой остановки), проверить содержимое обеих игр и только затем запускать новый сервис. Копирование только основного файла живой WAL-базы недопустимо.

До DNS/публичного запуска проверить оба образа на изолированных volumes и сохранение после пересоздания контейнера. Для пробного запуска использовать отдельные имена проекта/volumes и не создавать `iva-games` контейнеры параллельно на одной базе. Этот шаг должен включать backup/restore в новый volume; одной сборки недостаточно для принятия эксплуатации.

## 5. Первый публичный запуск

До этой точки должны быть подтверждены: целевой сервер, свободные порты либо интеграция с его текущим proxy, реальные SMTP-настройки, принятые образы, сохранение/восстановление данных и выбранный объём Telegram. DNS A (и AAAA только при действительно работающем IPv6) для `iva-games.pro` и `chess.iva-games.pro` должен указывать на выбранный сервер. Не менять записи старых шахматных доменов как побочный эффект.

После проверки DNS и разрешённого запуска:

```bash
deploy/iva-games/compose.sh up -d --no-deps --no-build --pull never --wait --wait-timeout 120 chess platform
deploy/iva-games/compose.sh up -d --no-deps --no-build --pull never caddy
curl --fail --silent --show-error https://iva-games.pro/health/ready
curl --fail --silent --show-error https://chess.iva-games.pro/api/health
curl --fail --silent --show-error https://chess.iva-games.pro/api/overdrive/health
```

Caddy получает сертификаты только после доступности доменов и внешних портов; первый HTTPS-запрос может потребовать повторения после выдачи сертификата. Health не доказывает доставку почты, успешную партию или достаточную производительность сервера. В двух независимых браузерах пройти регистрацию/подтверждение на согласованных адресах, дружбу, приглашение, «Пробный стол», отдельную гостевую партию каждой шахматной игры и reconnect. В Форсаже новая партия должна использовать v2, сохранённая v1 — прежние правила. Подтвердить RU/EN, мобильный интерфейс на реальном устройстве и звук, если эти пункты ещё не приняты.

## 6. Резервная копия и обычное обновление

`backup.sh` кратко останавливает **только указанный** сервис, требует чистого завершения, копирует весь `/data`, проверяет обе базы через `PRAGMA quick_check` в отдельной копии и запускает тот же исходный контейнер. Chess и platform копируются раздельно. На ошибке остаётся маркер `INCOMPLETE`; такую копию не использовать для восстановления. При аварийном прерывании проверить состояние сервиса. Каталог назначения должен быть новым, его родитель — уже существовать.

```bash
backup_stamp="$(date -u +%Y%m%dT%H%M%SZ)"
deploy/iva-games/backup.sh platform "/srv/iva-games-backups/platform-$backup_stamp"
```

Для шахмат заменить оба `platform` на `chess`. Это техническое обслуживание с кратким разрывом соединений выбранного приложения; автоматического режима «не принимать новые комнаты и дождаться всех партий» пока нет. Выбирать момент без активных партий/согласованное окно, проверить восстановление после запуска. Не заявлять бесшовное обновление.

Резервировать также приватные env-файлы и ключ Telegram отдельно, с ограниченным доступом. Хранить защищённую копию вне сервера и периодически проверять восстановление. Копия на том же диске не покрывает потерю сервера. Скрипт не задаёт расписание и сам ничего наружу не отправляет.

Для выпуска **только портала**:

1. Собрать и проверить новый `iva-games-platform:<SHA>`, сохранить предыдущий образ и `release.env`.
2. Сделать проверенную копию `platform`, сохраняя оба SQLite-файла вместе.
3. Изменить **только** `PLATFORM_IMAGE` в приватном `release.env`; имена volumes оставить.
4. Выполнить команду ниже; не использовать общий `down` и не пересоздавать Caddy/шахматы.

```bash
deploy/iva-games/compose.sh up -d --no-deps --no-build --pull never --wait --wait-timeout 120 platform
curl --fail --silent --show-error https://iva-games.pro/health/ready
```

Для шахмат — такой же порядок с `CHESS_IMAGE`, backup `chess` и целевым сервисом `chess`. Проверить, что ID/StartedAt другого контейнера не изменились. Изменение общих пакетов может требовать выпуска обоих потребителей; выбор делать по фактическому diff от последнего успешно опубликованного SHA каждого образа.

## 7. Откат приложения и восстановление данных — отдельные операции

При неудачном обновлении сначала проверить совместимость предыдущего приложения с текущей схемой и версиями партий. Для совместимого отката вернуть прежний `PLATFORM_IMAGE` либо `CHESS_IMAGE` и выполнить ту же точечную команду `up`. **Не восстанавливать старую SQLite-копию автоматически:** это потеряет действия пользователей после backup. Прежняя версия Форсажа с протоколом v1 не является безопасным откатом для уже созданных v2-партий; сохранить совместимый v2-образ или исправить текущий.

Для испытания восстановления или явно принятого восстановления повреждённых данных:

1. Выбрать копию без `INCOMPLETE`, прочитать `service.txt`, `image-reference.txt`, `image-id.txt`, `revision.txt`; использовать совместимый сохранённый образ. Копия содержит все файлы `data/`.
2. Создать **новый** пустой volume с отдельным именем; предварительно убедиться, что такого volume ещё нет. Исходный рабочий volume не удалять и не перезаписывать.
3. В одноразовом контейнере из этого образа, без сети, смонтировать backup `data/` только для чтения и новый volume как `/data`; скопировать **весь** каталог и назначить владельца `node:node`. Например, после подстановки проверенных абсолютного пути, нового имени и образа:

```bash
# Задать restore_source, restore_volume и restore_image по выбранной копии.
if docker volume inspect "$restore_volume" >/dev/null 2>&1; then
  printf 'Volume already exists; choose a new name.\n' >&2
  exit 1
fi
docker volume create "$restore_volume"
docker run --rm --network none --user 0:0 \
  --mount "type=bind,src=$restore_source/data,dst=/backup,readonly" \
  --mount "type=volume,src=$restore_volume,dst=/data" \
  --entrypoint sh "$restore_image" -ceu 'cp -a /backup/. /data/; chown -R node:node /data'
```

4. Запустить проверку SQLite и приложение с новым volume в изолированном окружении, без доставки почты/Telegram; проверить учётные записи, комнаты и восстановленную партию. Изолированная проверка не подключается к живому webhook. Если требуется production-конфигурация для проверки, исходящую сеть блокировать и не запускать сценарии отправки.
5. Только после принятого решения о восстановлении остановить соответствующий рабочий сервис, указать новое имя `PLATFORM_DATA_VOLUME`/`CHESS_DATA_VOLUME`, совместимый образ и запустить только этот сервис. Другой сервис и его volume не менять. Зафиксировать, до какой точки восстановлены данные и какие более поздние действия отсутствуют.

Эта процедура не выполнялась на production и не является командой восстановить данные сейчас. Для штатного отката образа шаги замены volume не нужны.

## 8. Что проверено при подготовке пакета

Docker CLI/daemon в среде этой подготовки недоступны. Контейнерные сборки, Compose startup, получение сертификатов, живая почта/Telegram и операция backup/restore в Docker **не выполнялись**. Следующий исполнитель должен подтвердить их до публичного запуска и записать точные SHA, image IDs, команды и результаты.

В среде подготовки выполнены:

- `bash -n` для `compose.sh` и `backup.sh`, `git diff --check`.
- Разбор YAML через PyYAML; проверка трёх независимых сервисов, внешних volumes, отсутствия опубликованных внутренних портов и обязательного SMTP. Это не проверка схемы настоящим Compose.
- Сопоставление обоих Dockerfile с `package-lock.json`: все восемь workspace-манифестов копируются до `npm ci`. Старый `deploy/Caddyfile` совпал с исходным содержимым.
- Для гостевых ссылок: `npm run build:portal` (TypeScript и Vite), ESLint изменённого `App.tsx`, статический React-рендер анонимного начального состояния на RU/EN. Проверено наличие обеих локальных ссылок до загрузки аккаунта и наличие обоих публичных адресов в production bundle. Визуальный браузерный переход по новым ссылкам здесь не проверялся.
- Семь сценариев `backup.sh` с **контролируемой заглушкой Docker CLI**: успешная копия каждой пары БД, исходно остановленный сервис, нечистое завершение, отказ копирования, повреждённая база, уже существующий каталог назначения. Внутри сценариев реально выполнялся SQLite `quick_check` над обычными файлами через установленный `better-sqlite3`. Проверены повторный запуск исходного контейнера в сценарии ошибки, сохранение байтов исходных fixtures и маркер неполной копии. Это проверка управляющего скрипта, не настоящий контейнерный backup/restore.

Эти проверки не заменяют запуск контейнеров. Существующий CI `.github/workflows/iva-platform.yml` проверяет код, сборки и HTTP smoke. Он **ещё не разворачивает сервер после push**. Автопубликация подключается после принятия этого первого выпуска: использовать сохранённые SHA образов, последовательные обновления по сервисам, проверку здоровья и совместимый откат. Доступы сервера/registry в этой подготовке не предполагались и не создавались.

Отдельно подготовлен `.github/workflows/iva-release-check.yml`: PR matrix собирает оба Dockerfile на GitHub-hosted Ubuntu runner и запускает каждый production runtime без внешней сети (`--network none`). Проверяются штатный healthcheck образа, содержимое health-ответов, HTML и реальные JS/CSS-ресурсы, гостевая/анонимная сессия через API, схемы и целостность двух SQLite-баз, работа от непривилегированного пользователя и сохранение записей после замены контейнера на том же volume. Для platform заданы **только CI-заглушки** `SMTP_HOST=mail.invalid` / `SMTP_FROM=ci@example.invalid`; SMTP-сервера нет, отправка писем не вызывается, Telegram выключен. Это не приёмка доставки почты. Production guard не изменён. Workflow имеет только `contents: read`, не получает секреты, не отправляет образы, не разворачивает сервер и не загружает artifacts. **Фактический запуск этого workflow ожидается после публикации; файл workflow сам по себе не является пройденной проверкой Docker.**

Официальные основания: [Docker build context и .dockerignore](https://docs.docker.com/build/concepts/context/), [Compose env_file raw](https://docs.docker.com/reference/compose-file/container-spec/#format), [выборочный Compose up](https://docs.docker.com/reference/cli/docker/compose/up/), [Caddy reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy). Контракты приложений сверены с `apps/platform/src/config.ts`, `apps/platform/src/http.ts`, `apps/server/src/main.ts` и соответствующими сборочными конфигурациями.
