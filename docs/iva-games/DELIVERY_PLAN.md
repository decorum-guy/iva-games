# Iva Games — порядок реализации и приёмки

Дата: 25 ноября 2026 года. **План, не отчёт о выполненной реализации.** Владелец поручил записать две идеи и подробно проработать одну. Продуктовая разработка новых игр начинается после работающего общего фундамента; концептуальные правила разрабатываются уже сейчас.

## Этап 0. Согласовать кодовую базу

Вложенный перенос продолжен от локальной миграции `9ecf362`, документы платформы интегрированы из `635520c`. Результаты и оставшаяся проверка записываются в [VALIDATION_IVA_GAMES_LAYOUT.md](../VALIDATION_IVA_GAMES_LAYOUT.md). Перед следующей работой прочитать актуальные remote refs и локальные изменения; не перезаписывать пакетный код из старой main или документационного снимка.

Текущая структура: games/chess/remorse, games/chess/overdrive, packages/engine-sdk и apps/server. games/district и games/harbor пока содержат только концептуальные документы. Рабочее имя общего репозитория — iva-games. Переименование по прежнему распределению работ выполняет владелец; при изменении remote использовать stable repository ID и фактически возвращённый URL, а не угадывать адрес.

При последующих изменениях повторять затронутые проверки импортов, workspaces, сборок обоих клиентов/сервера, ресурсов, комнат и сохранений; живой проход выполнить по [заданию локальному агенту](../../prompts/ACCEPT_OVERDRIVE_MONOREPO.md). Старые имена баз и ключи профиля сохраняются. Проход TypeScript не заменяет загрузку клиента и приёмку нужных сценариев на устройстве.

**Результат:** собранные шахматные приложения работают из новой структуры, а фактический статус и оставшиеся ограничения записаны. Текущая живая приёмка Remorse/Форсажа сохраняется отдельной задачей; этот план не объявляет её завершённой.

## Этап 1. Аккаунты и друзья

Реализовать минимальный профиль, настоящий вход/выход и восстановление доступа по выбранной спецификации, устойчивые playerId учётных записей, приглашение в друзья, принятие/отклонение, удаление и блокировку. Поиск по точному публичному идентификатору или ссылке; без импорта чужих адресных книг.

**Приёмка:** два независимых профиля проходят вход, отправляют и принимают запрос; повтор запроса не создаёт дубликат; блокировка запрещает новые обращения; удаление дружбы не удаляет чужой аккаунт и не повреждает историю партий. Все ошибки видимы в интерфейсе. Реальная почтовая доставка, если нужна выбранному входу, проверяется отдельно на разрешённом тестовом получателе, не подменяется записью кода в лог.

## Этап 2. Общие комнаты и приглашения на сайте

Реализовать session-kit и platform room registry, вместимость, готовность, устойчивые места, приватную ссылку и адресные приглашения друзьям. Для проверки каркаса использовать маленькую техническую сессию на 2–6 игроков с одним публичным и одним приватным действием; она не считается новой продуктовой игрой.

**Приёмка:** вход по ссылке/адресному приглашению, гонка двух подтверждений за последнее место, повтор команды после обрыва, отказ постороннему пользователю, повторное подключение и перезапуск сервиса, неизвестная версия, истечение и отзыв приглашения. Никто не получает чужой приватный payload через события или восстановление. Недоступная игра не превращает принятое приглашение в фиктивно начатую партию.

В этой фазе выбрать и проверить ровно одного владельца места в комнате. Если registry и игровой процесс имеют отдельные базы, применять устойчивую идемпотентную процедуру reserve/commit/reconcile; не обещать распределённую транзакцию из двух локальных SQLite-транзакций.

## Этап 3. Telegram-приглашения

Реализовать кнопку подключения, одноразовую ссылку, /start, подтверждение найденного Telegram-аккаунта на сайте, управление согласием, доставку приглашения и переход к его текущему состоянию. Спецификация: [TELEGRAM_LINKING](TELEGRAM_LINKING.md).

**Приёмка без реальной отправки:** истёкший/повторно использованный/пересланный код, второй Telegram-аккаунт, группа вместо личного чата, webhook с неверным секретом, повтор update, отозванное приглашение, блокировка между игроками, отключённая доставка, неизвестный результат send, повтор worker после рестарта. Mock-проверки не доказывают реальную доставку.

**Живая приёмка:** отдельно с разрешёнными владельцем тестовыми участниками и подтверждёнными аккаунтами проверить связку сайта, бота и возвращение в правильную комнату. Записать различие между принятой API отправкой, фактически увиденным сообщением и принятым приглашением. Не использовать тесты как разрешение рассылать друзьям пользователя.

Для запуска потребуются фактическое имя/токен бота, HTTPS адрес и серверные настройки. В этом пакете они не созданы и не запрашиваются: сначала готовится код и воспроизводимая проверка.

## Этап 4. Выпуск фундамента

Связать CI, сборку и серверную публикацию. Определять затронутые приложения и зависимости, хранить успешный SHA по приложению, проверять работоспособность, сохранять предыдущую совместимую сборку, не терять актуальные данные при откате.

**Приёмка:** изменение портала не перезапускает игровые сессии; исправление конкретного игрового сервиса не перезапускает другие независимые сервисы; общая библиотека запускает проверки потребителей; неудачный выпуск не теряет изменения для следующего; занятая комната обрабатывается по принятой политике обновления. Резервная копия проверяется восстановлением в изолированную базу.

Записи экранов и трассы приёмки остаются локальными. В Git — исходники, необходимые рабочие ресурсы и короткие текстовые отчёты; большие QA-артефакты не выгружаются в GitHub Actions. Релизные сборки имеют ограниченное хранение и очистку.

## Этап 5. «Район»: от правил к первой настоящей партии

1. Независимо прочитать [правила v0.1](../../games/district/RULES_V0_1.md), проверить расчёты, пределы решений и завершение каждого раунда.
2. Провести бумажную/табличную пробу; числа из документа считать исходными гипотезами. Этот документ такой пробы не проводил.
3. Реализовать чистое ядро и минимальную сетевую версию на готовом session-kit. Сначала подтвердить целую партию вдвоём, затем втроём/вчетвером.
4. Пройти игровую обратную связь: ясность дохода, ценность действий проигравшего торги, выгодность соседства, длительность ожидания и возможности отстающего.
5. Подготовить собственную визуальную систему, короткое обучение и звук по конкретным игровым событиям. Проверить читаемость на телефоне.
6. Выпустить после приёмки завершённой партии, восстановления и скрытых ставок; не присваивать непроверенные Elo или оценки баланса.

**Первый продуктовый результат:** двое вошли по приглашению, поняли ход раунда, завершили партию и смогли повторить её без помощи разработчика. Четыре участника проходят тот же путь. Готовность не измеряется числом созданных экранов.

## Этап 6. «Гавань»

Доработать [концепцию](../../games/harbor/CONCEPT.md) до полного набора правил. Независимо проверить договоры, резервирование товара/денег/мест, разрешение перевозок, исходы при уходе участника и возможность продолжить партию без его дальнейшего согласия.

Первая проба ориентирована на 3–6 человек. Не обещать полноценный режим для двоих и не растягивать шахматный поиск на скрытые сведения. После проверки торговли — ядро, сеть на уже принятом фундаменте и художественная приёмка.
