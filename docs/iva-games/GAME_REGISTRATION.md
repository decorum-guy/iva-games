# Добавление игр и автоматическая доставка

## Один реестр

`packages/game-registry/games.json` — общий источник каталога и гостевых шахматных запусков. Запись содержит ID, коллекцию, названия и описание RU/EN, число участников и доступность **комнат платформы**. Гостевой запуск задаётся отдельно блоком `chess`.

Этот блок задаёт npm workspace, исходную папку, публичный путь, адрес разработки и при наличии серверного runtime — его health/protocol и имя SQLite-базы. Сейчас в реестре REMORSE (`/`), OVERDRIVE (`/overdrive/`) и COLOSSUS (`/colossus/`). Район и Гавань тоже берут тексты каталога из этого файла; существующая регистрация рабочего runtime Района сохраняет свой доступный статус.

Из реестра автоматически получаются:

- карточка в шахматном каталоге, тексты RU/EN и ссылка «Играть»;
- список npm workspace для `build:client`, объединение статических сборок и SPA-путь chess-сервера;
- health-проверки образа и перечень объявленных игровых баз в проверках сохранности;
- входы образов для автодеплоя: изменение реестра обновляет portal/platform и chess, а изменение исходников одной шахматной игры — chess;
- dependency closure каждого зарегистрированного шахматного workspace, включая его новые внешние зависимости.

Исходники Района или его частные зависимости по-прежнему меняют только platform fingerprint. Новые workspace обнаруживаются и проверкой границ пакетов. Dockerfile больше не содержит отдельный `COPY package.json` для каждой игры.

## Как добавить следующую шахматную игру

1. Создать `games/chess/<id>` с обычным npm workspace, локальными ассетами, скриптом `build` и Vite-сборкой в собственный `dist`. Пути ассетов должны быть уникальны: например `/assets/<id>/…`. Общая сборка проверяет конфликты байтов и не перезаписывает чужие ассеты.
2. Добавить **одну запись** в `packages/game-registry/games.json`. Для готовой гостевой игры указать `chess.workspace`, `chess.source`, `chess.route` и `chess.developmentUrl`. Пока аккаунтные комнаты не подключены, оставить `roomStatus: "unavailable"`; гостевая кнопка при этом работает.
3. Выполнить `npm install --package-lock-only`, затем `npm ci`, `npm run check` и `npm run build:all`. Общий lockfile сохраняется один.
4. Опубликовать проверенную рабочую ветку/PR. После отдельно разрешённого объединения в `main` существующий pipeline проверяет, собирает, публикует и передаёт образы штатному обработчику выпуска. Новых прав, отдельного workflow или ручного списка ссылок для гостевой игры не требуется.

Настроенный `VITE_<ID>_URL` сохраняет возможность изменить ссылку конкретной игры; общий production-origin хранится в `chessOrigin`. Локальный адрес берётся из `developmentUrl`.

Реестр не создаёт правила, бота, API, БД или аккаунтный runtime. Если игре нужна сеть, её обработчик по-прежнему реализуется и подключается на сервере; только после этого объявляются реальные health/protocol/database. Общие комнаты портала требуют настоящего адаптера платформы. Добавление записи не должно изображать такой адаптер работающим. Для новой схемы БД обязательны собственные проверки хранения и миграций.

## Доставка Колосса

Текущий кандидат обновляет существующий chess-сервис третьим клиентом, отдельным API и `colossus.sqlite`. Compose задаёт его путь в постоянном `chess-data`. Проверка release-image включает оба гостевых клиента Колосса, команду, замену контейнера и точный повтор квитанции без второго расхода команды. Проверяются три игровые базы. Backup сохраняет весь `/data`, проверяет объявленные и присутствующие `.sqlite` и остаётся совместимым с прежними образами без файла реестра. Restore использует закреплённый образ и новый изолированный volume.

Autodeploy workflow, production environment, защита main, серверная блокировка и проверка неизменяемых образов сохранены. **Публикация feature-ветки сама по себе не обновляет production.** Проверенный источник, успешный CI и установленная версия сервера — отдельные факты.

## Проверки этого изменения

- 17 тестов реестра: дополнительная игра получает RU/EN-метаданные, гостевую ссылку, build-workspace и SPA-путь; реальный временный четвертый клиент объединён общим скриптом без его редактирования; повторные/небезопасные ID, workspace, пути, health и базы отклоняются; обязательна корневая игра, зарезервированные маршруты API/ассетов запрещены.
- 14 Python-проверок fingerprint: зарегистрированный новый workspace и его частная зависимость учитываются, правка реестра затрагивает оба образа, District-only изоляция сохранена.
- `check:boundaries`, `typecheck:platform`, `build:server`, `build:foundation` и целевой ESLint прошли.
- `platform:smoke`: два HTTP-клиента, бот, три раунда, побайтовая статика и перезапуск/повтор прошли; внешних сообщений нет.
- 9 тестов backup с настоящим SQLite/WAL и Docker CLI double, включая три шахматные базы; предыдущая полная инфраструктурная Python-матрица — 46 проверок; после неё добавлен один тест включения registry-validator в оба fingerprint. Это не запуск Docker или VPS.
- Колосс + общие static-layout тесты сервера: 25 прошли; версия чистого HTTP-drain/retry проверена на настоящем SQLite.
- Runtime Docker-проверки выполняет CI точного опубликованного SHA; локальная проверка shell-синтаксиса не называется выполнением контейнера.
