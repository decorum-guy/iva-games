# Район · выпуск текущего профиля через main

**Решение владельца, 28 ноября 2026:** обычный принятый выпуск `main` после CI должен обновлять версию игры для новых комнат без отдельного ручного флага на VPS. Текущий поставляемый профиль Района — `district@0.4`. `DISTRICT_TERRITORIAL_ENABLED` больше не читается; даже старое значение `false` не выбирает v0.3. Это прямое изменение прежнего порядка отдельной активации, а не разрешение обходить доступы или обязательные проверки доставки.

Сохранённые лобби и матчи продолжают свои закреплённые версии. Перед выпуском сверяй актуальные refs, CI и верх [BUILD_STATUS](BUILD_STATUS.md). Публикация этого контракта сама по себе не подтверждает доставку кода или игровую приёмку. Для проверки на Mac/VPS подготовлено [самостоятельное задание](../../prompts/ACCEPT_AUTOMATIC_DISTRICT_RELEASE.md).

**Происхождение реализации:** исследование и правила — PR №21 `bab999ec201c24725e17813ea30723c11431dc38`; территориальный кандидат — PR №24; переработанный интерфейс — PR №26; независимый аудит и исправления — [PR №27](https://github.com/decorum-guy/iva-games/pull/27). [Отчёт аудита](../../games/district/VALIDATION_INDEPENDENT_AUDIT_2026_11_27.md) относится к указанным в нём ревизиям. Решение 27 ноября разрешило самостоятельные проверки и main-выпуск без ожидания совместной партии; решение 28 ноября дополнительно убрало ручной флаг.

## Хранение и откат

- В существующем runtime-volume появляются две таблицы `district_territorial_matches` и `district_territorial_receipts`. Прежние комнаты, `district_matches` и `district_action_receipts` обслуживает исходный адаптер.
- У новых матчей префикс `d4-`. Runtime сохраняет readers v0.2/v0.3/v0.4. Закреплённые настройки существующего лобби не меняются при его чтении или старте после обновления; начатая партия сохраняет правила, карту, данные, новости и потоки случайности.
- Откат допустим только на образ, который умеет читать все уже созданные лобби и сохранения. После появления v0.4 нельзя возвращаться к образу с поддержкой только v0.2/v0.3, удалять новые матчи или восстанавливать старую БД поверх актуальной. При несовместимости исправлять вперёд, сохраняя поддержку активных партий. Это требование совместимости данных; ручного разрешающего флага для обычного выпуска нет.
- Использовать согласованное резервирование platform и runtime SQLite штатным обработчиком выпуска с релизным манифестом. Восстановление проверять на отдельных volumes. На изолированной копии должны открываться и продолжаться старые v0.2/v0.3 и сохранённая v0.4; новая комната должна получать текущий профиль приложения.

## Выпуск

1. Сверить актуальные ветки, принятый SHA и полный CI итоговой ревизии. Проверить сохранение версий существующих лобби/матчей и выбор v0.4 для новой комнаты. Проверка конфигурации должна охватывать отсутствие старой переменной и оставшееся `DISTRICT_TERRITORIAL_ENABLED=false`: оба случая дают текущий профиль.
2. Публиковать согласованное изменение в `main` через действующие проверки и доставку образов. Сохранять штатные `release.lock`, проверку происхождения, резервирование, обработку `pending.json` и выбор сервисов по изменившемуся коду. При изменении только platform шахматы и Caddy не пересоздаются. Не повторять принятую установку host-скриптов, SSH/firewall или DNS без конкретного выявленного дефекта.
3. Подтвердить точную строку `DEPLOYED <sha>` для итогового выпуска. Успешная сборка образов или завершение с `superseded` этого не заменяет. Проверить три health и `https://iva-games.pro/api/platform/v1/games`: для `district` должны возвращаться `rulesVersion: district@0.4`, `contentVersion: district-territorial@1`, `status: available`.
4. В разрешённой контрольной комнате по HTTPS проверить новую v0.4 двумя независимыми клиентами: карту и пресет, бота, старт, обычное действие, сделку, возврат и согласованный итог. Сохранённые старые версии должны по-прежнему открываться и продолжаться. Полные проверки рестарта и редких исходов выполнять на изолированном стенде; не перезапускать production ради теста и не менять чужие партии.
5. При существующем административном доступе можно удалить устаревший ключ `DISTRICT_TERRITORIAL_ENABLED` из приватного `platform.env`, сохранив остальные значения и права файла. Это уборка конфигурации: она не требуется для выбора v0.4 и не требует отдельного рестарта. Не печатать env или секреты; ограниченный CI-ключ не даёт произвольного административного доступа.

Зафиксировать итоговый SHA, Actions, ответ каталога, фактические игровые проверки и оставшиеся ограничения в BUILD_STATUS и компактном отчёте. На доступном VPS дополнительно сверить state/pins/pending и неизменность chess/Caddy для platform-only выпуска. Если конкретной возможности нет, назвать непроверенную часть; не приписывать ей успешный результат.

## Локальная приёмка и запуск

```sh
npm ci
npm run check
npm run build:all
node scripts/district-territorial-browser.mjs
npx vite build --config games/district/vite.territorial-simulation.config.ts
node .qa/territorial-runner/simulate.mjs --samples=9
scripts/district-territorial-demo.sh start
scripts/district-territorial-demo.sh open
```

Демо использует `127.0.0.1:4380`, отдельные platform/runtime SQLite и отдельный профиль Chrome. `scripts/district-territorial-demo.sh stop` останавливает только это демо. Ссылку на лобби печатает команда `start`. Тренировка доступна отдельно. [Тренировка](http://127.0.0.1:4380/district-training)

- Целевые проверки находятся в `games/district/tests/territorial-{maps,news,runtime,tutorial}.test.ts`. Они покрывают отказ транзакции после обновления состояния, потерю ответа, повтор, SQLite reconnect и старые снимки. Браузерные fixtures используют временную базу.
