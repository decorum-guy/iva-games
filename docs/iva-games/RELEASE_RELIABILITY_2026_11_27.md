## 2. GitHub: авторизация, диагностика и сохранение проверок

`activation.py` теперь содержит общий ограниченный по времени `github_json()`. Runner читает актуальный main через новый `github-main.py`; сервер использует тот же авторизованный запрос для main и успешного platform CI. Применяется существующий краткоживущий token GitHub Actions. Deploy job получает необходимые `contents: read`, `actions: read`, `packages: read`.

Токен передаётся VPS через прежний stdin-протокол, не аргументами и не постоянным файлом. Redirect отклоняется до пересылки Authorization другому адресу. При ошибке нет перехода к анонимным запросам. Повторы ограничены; неизвестный 403 не повторяется бесконечно. В диагностику попадают статус и проверенные безопасные request/rate-limit headers, без тела ответа или приватной конфигурации.

Сохраняются проверки актуального main, успешного CI, digest, source/revision образа и совместимости. Проверки публичного health не получают GitHub token. Официальные основания для поведения API: [лимиты и способы авторизации GitHub](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [права чтения workflow runs](https://docs.github.com/en/rest/actions/workflow-runs).

## 3. Остановка приложений

Оба Dockerfile уже запускали Node непосредственно под Compose init. Подтверждения проблемы shell/PID forwarding не найдено. В старой реализации ожидание активного HTTP могло оставаться неограниченным.

На собранном исходном `5abba982` независимый исполнитель воспроизвёл остановку при заторможенном чтении большого статического ответа: оба процесса оставались живы до освобождения клиента на седьмой секунде. Исправленные процессы завершались примерно за пять секунд без освобождения клиента. Это подтверждает дефект ограниченного drain, но не доказывает, что именно такой клиент вызвал исторический 60-секундный сбой VPS.

Новый `packages/session-kit/src/http-lifecycle.ts`:

- прекращает приём новых соединений;
- даёт активному HTTP пять секунд, затем закрывает оставшиеся HTTP-сокеты;
- отдельно ждёт обещания принятых обработчиков и события закрытия ответов;
- возвращает одно и то же обещание при повторном close;
- не считает уничтоженный сокет отменой прикладной операции.

Шахматный сервер завершает HTTP и обе группы WebSocket до закрытия хранилищ. Platform прекращает новые reconciliation batches, завершает HTTP, затем ждёт текущую reconciliation, реальные runtime promises и Telegram work. Только затем закрывает транспорт и SQLite. Promise.race, вернувший `GAME_TIMEOUT`, не исключает продолжающуюся операцию адаптера из ожидания.

Оба production entrypoints имеют 30-секундный watchdog с ненулевым завершением при неудаче. Это граница исправления зависшего I/O, не гарантия против навсегда заблокированного event loop; крайний Docker timeout остаётся отдельным аварийным механизмом.

## 4. Согласованная копия без остановки старого процесса

Новый `backup.sh SERVICE /absolute/new/destination` работает только с заданным сервисом. Работающий контейнер кратко замораживается; весь `/data`, включая SQLite WAL/SHM, копируется вместе. Контейнер возвращается к работе до проверки отдельной временной копии на исходном образе. Уже остановленный контейнер не запускается; заранее paused контейнер не принимается автоматически.

Копирование ограничено 20 секундами. CLI-вызовы имеют свои тайм-ауты. Флаг необходимости unpause выставляется до команды pause, поэтому потерянный ответ Docker не лишает cleanup информации. Ошибки, TERM и INT запускают cleanup. `INCOMPLETE` снимается только после возврата контейнера и успешного `quick_check` обеих баз. Проверка восстановления принимает только завершённую копию и создаёт новый volume; живые данные автоматически старой копией не заменяются.

`activation.command()` даёт backup время на cleanup при внутреннем timeout и внешней отмене. TERM/INT пересылаются дочерней группе, а родитель удерживает настоящий release lock до завершения ограниченной очистки. Повторные сигналы не прерывают её и не продлевают deadline. Общий CI wrapper имеет достаточное окно для этого завершения.

Нельзя обещать разморозку при потере питания, SIGKILL, недоступном Docker или неисправимом cleanup. Такой выпуск завершается неуспешно; оператор проверяет исходный контейнер, paused и маркер копии. Сам pause также задерживает ответы выбранного приложения и не является zero-downtime обновлением.

## 5. Почему Район мог затрагивать chess и что изменено

Прежний fingerprint включал в оба образа весь root package/lockfile и все workspace-манифесты. Изменение собственной зависимости Района могло сделать chess «изменившимся» при прежних шахматных исходниках.

Новый `image-inputs.py` использует Git index, исходники соответствующего сервиса, его build scripts и полные lock-записи достижимых npm-зависимостей. Учитываются вложенное разрешение, peer/optional зависимости и код связанных workspaces. Общий root toolchain учитывается консервативно обоими сервисами. Пропавшая обязательная запись останавливает выпуск. Скрипт сборки общего шахматного клиента также входит в его отпечаток.

`promote()` получает список действительно изменившихся digest. Только для него выполняются backup и `up --no-deps`, а при допустимом откате — прежний образ. Для неизменяемых сервисов и Caddy сохраняются и сравниваются ID, image ID, StartedAt, RestartCount, Running/Paused. Успех с неожиданно перезапущенным неизменяемым сервисом не объявляется. Итог записывается в `last-deploy.json` без env контейнеров.

Это проверяет больше, чем один совпадающий image digest: перезапуск того же образа тоже обнаруживается. Отдельные тесты подтверждают отсутствие самого вызова backup/up chess при platform-only обновлении и откате. Живая непрерывная шахматная партия остаётся обязательной внешней приёмкой.

## 6. Что обнаружил независимый review

Два замечания были исправлены до итоговых прогонов:

1. После response timeout исходная runtime promise могла ещё писать в SQLite. Добавлены её учёт и последовательное ожидание после HTTP drain. Регрессия делает настоящую отложенную SQLite-запись после истечения лимита ответа.
2. Внешний TERM мог убить activation, оставив отдельную группу backup и освободив lock раньше cleanup. Изолированное воспроизведение показало живого child и доступный lock. Теперь регрессия с настоящими `main()`, `flock` и процессами проверяет удержание lock, повторные сигналы, завершение cleanup и освобождение lock после него.

Первый общий `npm run check` выявил ещё одну гонку нового теста: callback `server.close` мог опередить событие `ServerResponse.close`. Независимый TCP-пример воспроизвёл это в 30/30 случаях. Исправлен сам lifecycle, добавлено ожидание закрытия ответа; assertion не удалён. Исполнитель получил 0/30 ранних завершений, затем общий check прошёл.

## 8. Что ещё требуется на VPS

1. Точечно установить проверенные `activation.py`, `backup.sh`, `ci-deploy` в `/opt/iva-games/deploy` через административный SSH **до** использования исправления. Образы эти файлы не обновляют. Не повторять `install-host.sh` и не перезаписывать настройки шаблонами.
2. Принять первый инфраструктурный выпуск. Оба runtime и схема fingerprint меняются: обновление обоих приложений допустимо. Старые уже работающие процессы ещё не имеют нового shutdown, поэтому первый stop может сохранять старое поведение.
3. Учесть консервативную compatibility boundary: весь `packages/session-kit/src` входит в platform compatibility hash. Новый lifecycle может запретить автоматический rollback даже без изменения таблиц. Не ослаблять gate; при ошибке сохранять pending и выбирать проверенное исправление/восстановление оператором.
4. Выполнить следующий маленький выпуск только District/platform. Требуются `changed: ["platform"]`, отсутствие pause/backup/stop/up chess, неизменность chess/Caddy и продолжающаяся контрольная шахматная партия во время доставки.
5. Зафиксировать реальные Actions run, HTTPS, pins/state/pending, выбранные digest и результаты партий в новом отчёте. Лишь после этого можно утверждать, что исправленный автодеплой принят на работающем сервере.
