# Адрес игрока и лимиты за Caddy

## Исправленная проблема

До изменения HTTP-серверы брали адрес из `request.socket.remoteAddress`. В подготовленной схеме этот адрес принадлежит Caddy, поэтому у всех посетителей получался общий бюджет: в частности 10 регистраций и 5 запросов восстановления в час на весь портал, а также общие HTTP/WS-лимиты шахмат.

## Действующий контракт

- Server-only export `@iva-games/session-kit/http`; основной browser-facing export пакета не меняется.
- `TRUSTED_PROXY_IPS` — необязательный список точных IP TCP-peer, через запятую. Пустой список по умолчанию игнорирует все переданные клиентом адресные заголовки. Hostnames, CIDR, wildcard и `true` не допускаются.
- При совпадении socket peer принимается только один валидный IPv4/IPv6 из `X-Iva-Client-IP`. IPv6 и IPv4-mapped адреса нормализуются; порт, цепочка, несколько значений, zone ID и malformed IP не становятся идентичностью клиента. При отсутствии/ошибке заголовка остаётся socket IP. `X-Forwarded-For` не используется.
- Caddy **перезаписывает** `X-Iva-Client-IP` своим `{remote_host}` и для HTTP, и для WebSocket. Присланный посетителем заголовок не сохраняется.
- В Compose один `CADDY_PROXY_IP` одновременно задаёт статический адрес Caddy и доверенный peer обоих приложений. Upstream-порты по-прежнему не публикуются на хост.
- Пример подсети: `IVA_NETWORK_SUBNET=172.30.239.0/24`, динамический пул `IVA_NETWORK_DYNAMIC_RANGE=172.30.239.128/25`, Caddy `172.30.239.2`. Статический адрес находится вне динамического пула, чтобы приложения, запущенные до Caddy, не заняли его адрес.

## Перед размещением

Сверить пример подсети с действующими Docker/VPN/LAN маршрутами VPS. При конфликте согласованно выбрать подсеть, её динамический пул и свободный статический Caddy IP вне пула. Это настраивается до первого запуска; изменение сети работающего размещения потребует отдельного пересоздания контейнеров и не относится к обычному обновлению приложения.

Данная конфигурация предполагает прямой вход клиента в Caddy. CDN или ещё один reverse proxy перед Caddy требуют отдельной проверки доверенной цепочки; включение такой прослойки без неё снова сгруппирует клиентов по IP переднего proxy. Не заменять `{remote_host}` на недоверенный входящий заголовок.

Если используется существующий proxy вместо включённого Compose Caddy, задать его фактический socket IP в приложениях, закрыть прямой публичный доступ к upstream и обеспечить перезапись заголовка из проверенного адреса. Не расширять доверие на весь Интернет. Для уже работающего Caddy проверять конфигурацию через `exec`, а не создавать второй one-off контейнер с тем же статическим IP.

Cookie, Host/Origin и CSRF проверяются прежней логикой. Production cookie портала `__Host-iva_session` остаётся Secure/HttpOnly/SameSite=Lax/Path=/ без Domain; secure выбирается из HTTPS public origin, поэтому внутренний HTTP между Caddy и приложением этому не мешает. У шахмат отдельные guest cookies, общий аккаунтный адаптер этим исправлением не появляется.

## Выполненные проверки

- `npx vitest run packages/session-kit/src/http.test.ts apps/server/tests/trusted-proxy.test.ts apps/platform/tests/platform.test.ts` — 43 теста в 3 файлах прошли.
- `npx tsc --noEmit -p apps/server/tsconfig.json` — прошёл.
- ESLint всех изменённых TS-файлов helper/server/platform и Vite config — прошёл.
- `git diff --check` — прошёл.

Проверки используют loopback HTTP и WebSocket upgrade-запросы: разные адреса за одним доверенным peer имеют разные бюджеты, один адрес остаётся ограниченным, поддельные заголовки от недоверенного peer не меняют бюджет. Доставка SMTP/Telegram и новый VPS не проверялись. Живой Caddy/Compose runtime здесь пока не запускался; общие сборки и инфраструктурные проверки фиксируются в отчёте готовности выпуска.

## Другие результаты read-only аудита

- Runtime-конфигурация и public links уже используют `iva-games.pro` / `chess.iva-games.pro`; `iva-games.online` в проверенных runtime/deploy/CI файлах отсутствует.
- Публичный `GET /api/platform/v1/games` и статика не требуют аккаунта; SPA fallback допускает прямые ссылки `/chess`, `/games`, `/verify`, `/reset-password`.
- SMTP обязателен для production. Пустые host/from останавливают запуск; plaintext SMTP без STARTTLS не используется. Health подтверждает работоспособность процесса/БД, а не доставку письма, поэтому на VPS нужна проверка реальной разрешённой доставки подтверждения и сброса пароля.
- Telegram по умолчанию отключён. Сайт-приглашения работают независимо; включение требует полного набора реквизитов, HTTPS и явного proxy URL. Неполная включённая конфигурация отклоняется. Webhook регистрируется отдельно. Без активации не считать TG доставку работающей.

Официальная справка Caddy подтверждает overwrite через `header_up` и значение `{remote_host}`: https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#headers и https://caddyserver.com/docs/caddyfile/concepts#placeholders.
