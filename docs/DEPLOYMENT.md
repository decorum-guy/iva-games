# Публикация REMORSE

Целевой адрес владельца — **https://remorse.chess-2.online**. Корневой `chess-2.online` оставлен для будущего каталога после второй игры. Этот документ и конфигурация подготовлены в репозитории; они не подтверждают настроенные DNS, VPS, сертификат или доступ из Интернета.

## Один сервер для страницы и комнаты

`npm run build` собирает пакеты `games/chess/remorse` и `games/chess/overdrive`, объединяет их в `dist/` и создаёт `dist-server/main.js` из `apps/server` для Node. Отдельные клиентские результаты находятся в `games/chess/<game>/dist`; корневой `dist/` сохраняет адреса REMORSE `/` и OVERDRIVE `/overdrive/`. `npm start` отдаёт страницу, `/api/*` и WebSocket `/ws` с одного адреса. SQLite лежит отдельно от сборки. Нужен один процесс приложения: активные соединения хранятся в памяти процесса, поэтому несколько реплик пока не поддерживаются.

Статический `vite preview` оставлен для старых локальных проверок и звуковых демонстраций. Он не запускает комнаты. Для сетевого режима используется `npm start`.

### Локальная проверка на Mac

```sh
npm ci
npm run build
HOST=0.0.0.0 PORT=4175 DATABASE_PATH=.qa/online-acceptance.sqlite npm start
```

Открыть `http://127.0.0.1:4175` в двух независимых профилях браузера. Для телефона открыть LAN-адрес Mac с этим же портом. Первому игроку создать комнату, второму открыть приглашение; одному профилю не разрешается занимать оба места. При копировании приглашения для телефона открывать саму игру по доступному телефону LAN-адресу, чтобы ссылка не содержала `127.0.0.1`.

Для разработки — два терминала:

```sh
DEV_ORIGINS=http://localhost:5173,http://127.0.0.1:5173 npm run dev:server
```

```sh
npm run dev
```

Vite проксирует `/api` и `/ws` на `127.0.0.1:4173`. Изменения серверного TypeScript требуют повторного `npm run build:server`; `node --watch` перезапускает уже собранный сервер. `.env.example` можно скопировать в `.env` и передать Node через `node --env-file=.env dist-server/main.js`; файл не загружается сам и не должен попадать в Git.

## Подготовленная поставка через Docker Compose

В репозитории есть `Dockerfile`, `compose.yml` и `deploy/Caddyfile`. Docker устанавливает зависимости по общему lockfile и манифестам четырёх npm workspaces; серверный bundle включает чистые игровые модули и не требует TypeScript-исходников в runtime-образе. Приложение работает от непривилегированного пользователя, порт 4173 доступен только внутри Compose, снаружи открыты HTTP/HTTPS Caddy. Постоянные тома сохраняют базу и сертификаты между пересборками. Cookies ограничены поддоменом REMORSE.

До запуска нужны адрес и доступ к выбранному серверу. В DNS создаётся запись `A` для `remorse` на IPv4 сервера; `AAAA` добавляется только при работающем IPv6. Порты 80 и 443 должны доходить до Caddy. Пример рассчитан на сервер, где эти порты свободны; при существующем reverse proxy добавляется только виртуальный хост REMORSE, без замены чужих сайтов.

Пример ниже использует текущее имя GitHub `remorse-chess`. Владелец планирует переименовать существующий репозиторий в `iva-games`; после подтверждения нужно взять фактический clone URL из GitHub и обновить `origin` существующей копии. Сам перенос пакетов репозиторий не переименовывает.

На таком сервере:

```sh
git clone https://github.com/decorum-guy/remorse-chess.git
cd remorse-chess
docker compose up -d --build
docker compose ps
```

Caddy умеет проксировать WebSocket и автоматически получать/обновлять сертификаты для корректно настроенного публичного имени. Это возможности выбранного ПО, а не результат проверки нашего домена: [reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy), [automatic HTTPS](https://caddyserver.com/docs/automatic-https).

Проверка публикации — не только ответ страницы. Нужно получить `ok:true` от `https://remorse.chess-2.online/api/health`, создать комнату с одного устройства, зайти с другого через мобильную сеть, сделать взятие, увидеть одинаковый результат кубика, обновить одну страницу и завершить партию. Убедиться, что используется `wss://remorse.chess-2.online/ws` и cookie `Secure`, `HttpOnly`, без `Domain=chess-2.online`.

## Обновление и резервная копия

Перед обновлением создать согласованную копию SQLite. Скрипт использует API backup, учитывает WAL и не перезаписывает существующий файл:

```sh
docker compose exec remorse node apps/server/scripts/backup.mjs /data/before-release.sqlite
```

Имя для каждой новой копии должно быть новым. Копию следует вынести с сервера в выбранное владельцем хранилище. Не копировать только основной файл активной WAL-базы обычным `cp`. [Документация better-sqlite3 backup](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#backupdestination-options---promise).

У сервера есть также отдельная база OVERDRIVE. Для неё использовать тот же backup-скрипт с явным `DATABASE_PATH`, равным настроенному `OVERDRIVE_DATABASE_PATH` либо умолчанию `DATABASE_PATH + .overdrive.sqlite`. Копии двух игр не заменяют друг друга.

Обычное обновление:

```sh
git pull --ff-only
docker compose up -d --build
docker compose ps
```

Не удалять `remorse_data` и не запускать `docker compose down -v` при обновлении. После перезапуска комнаты восстанавливаются из базы, клиенты переподключаются. Уже выпавший кубик не бросается заново. Для отката кода использовать отдельную предыдущую сборку с совместимой схемой базы, сохранив актуальную базу и её резервную копию.

Локальные партии, настройки и Elo браузера привязаны к адресу сайта. Переход с `127.0.0.1` на домен не переносит их автоматически. Нужную локальную партию можно экспортировать до перехода и импортировать на новом адресе как тренировку; сетевые комнаты хранятся на сервере и не меняют локальный Elo.

## Ограничения первого запуска

- Дружеские комнаты, два игрока, без аккаунтов, чата, часов, поиска соперников и сетевого рейтинга.
- Незавершённая комната закрывается технически после 24 часов без игровых действий; heartbeat не продлевает срок. Завершённые результаты хранятся не меньше семи дней.
- Нужен один процесс Node и постоянный SQLite-том. Для масштабирования потребуется отдельная архитектурная работа.
- За reverse proxy HTTP/upgrade-лимиты пока относятся к адресу proxy: 180 HTTP-запросов в минуту и 60 WebSocket-подключений в минуту. Лимит игровых сообщений применяется к отдельному гостю. Перед массовым публичным запуском настроить доверенную передачу адреса клиента, не доверяя произвольному `X-Forwarded-For`.
- Docker/HTTPS и физический телефон проверяются на выбранном сервере и устройствах; успешные TypeScript и протокольные тесты этого не заменяют.
